# 기능 착수

기능 설명의 원본은 노션입니다. 레포에는 명세를 복사하지 않고 링크와 절만 남깁니다.

## 절차

1. **작업 트리**: `git status --short`로 기존 변경을 확인·보존합니다. 기본 브랜치(`develop`)에 있으면 `git fetch` 후 `<HM-키>/<짧은-작업명>` 브랜치를 만듭니다. 사용자가 병렬 작업을 원하면 `git worktree add <경로> -b <브랜치> origin/develop`을 씁니다. 브랜치 규칙은 [커밋 계약](../dino-commit/references/commits.md#commits)을 따릅니다.
2. **명세 확인**:
   - 노션 링크가 있으면 노션 도구(이름에 `notion`과 `fetch`가 들어간 도구)로 읽습니다.
   - 링크가 없으면 [노션 기능명세](../../../docs/domain/README.md#노션-기능명세)의 `구분(도메인)` 값으로 `[<도메인>] 기능명세`를 검색하고 `유효여부 O`인 페이지를 씁니다.
   - 노션 도구가 없으면 사용자에게 링크나 해당 절 내용을 요청합니다.
   - 필요한 것만 추립니다: 기능 목록의 해당 행, 데이터 명세, 상태 전이, 권한, 검증 정책, 수용 기준, 남은 확인 사항. 명세의 미결정 항목은 추정하지 않고 사용자에게 묻습니다.
3. **코드 기준 확인**: [도메인 지도](../../../docs/domain/README.md)에서 대상 모듈을 찾고 그 경로의 `AGENTS.md`를 읽습니다. 같은 모듈에서 가장 비슷한 기존 유즈케이스 하나(포트·서비스·테스트)를 골라 구조의 본보기로 삼습니다.
4. **PR 계획**: [PR 종류](../dino-pr/references/kinds.md#decide)와 [PR 단위](../dino-pr/references/planning.md#unit)로 나눕니다. 기본은 노션 기능 하나당 `유즈케이스` PR 하나입니다. 필요한 리팩터링은 선행 `구조 변경` PR로, 기존 계약을 깨는 변경은 `호환성 변경` 단계별 PR로 뺍니다.
5. **계획 파일**: 워크트리 루트 `<이슈키>-plan.md`(gitignore, 커밋하지 않음)에 아래 형식으로 씁니다.

   ```markdown
   # HM-000 <기능명> 계획
   - 노션: <링크> §<절>
   - 모듈: <module> (본보기: <비슷한 유즈케이스>)

   ## PR 1 — <종류>: <제목 초안>
   - 규칙: <명세에서 구현할 규칙 한 줄씩>
   - 선행: 없음 | PR n
   - 커밋: 1) <재현 테스트+구현 단위> 2) ...
   - 집중 검사: <테스트 클래스>
   - 완료 조건: <수용 기준>

   ## 미결정 (사용자 확인)
   - <명세의 남은 확인 사항·충돌>
   ```

6. **확인**: 계획 요약과 미결정 질문을 사용자에게 보이고 답을 받은 뒤 구현합니다. 구현은 `dino-architecture`와 `dino-testing`, 커밋은 `dino-commit`, 마무리는 `dino-pr` 스킬을 따릅니다.
