# 기능 착수

제품 결정은 노션 정책서, 필드·화면 흐름은 기능명세가 원본입니다([기획 원본 색인](../../../docs/planning/README.md#planning)). 레포에는 명세를 복사하지 않고 링크와 절만 남깁니다.

## 절차

1. **작업 트리**: `git status --short`로 기존 변경을 확인·보존합니다. 기본 브랜치(`develop`)에 있으면 `git fetch` 후 `<HM-키>/<짧은-작업명>` 브랜치를 만듭니다. 사용자가 병렬 작업을 원하면 `git worktree add <경로> -b <브랜치> origin/develop`을 씁니다. 브랜치 규칙은 [커밋 계약](../dino-commit/references/commits.md#commits)을 따릅니다.
2. **명세 확인**:
   - 세션에서 제품 동작을 바꾸는 첫 작업이면 [동기화 상태 확인](../../../docs/planning/README.md#status)을 먼저 합니다. `밀림`이면 구현 전에 알리고 [동기화](../../../docs/planning/README.md#sync)를 별도 커밋으로 먼저 합니다.
   - 노션 링크가 있으면 노션 도구(이름에 `notion`과 `fetch`가 들어간 도구)로 읽습니다. 본문은 페이지 전체(문서당 1만 토큰 이상)가 오므로 하위 에이전트에 읽혀 필요한 절의 요지만 받습니다.
   - 링크가 없으면 [기획 원본 색인](../../../docs/planning/README.md#baseline)에서 대상 모듈의 정책서·기능명세 링크를 찾습니다.
   - 노션 도구가 없으면 사용자에게 링크나 해당 절 내용을 요청합니다.
   - 필요한 것만 추립니다: 정책서의 권한·상태 전이·제한·검증 정책과 확정 필요 항목, 기능명세의 기능 목록 해당 행·데이터 명세·수용 기준. 화면설계는 근거로 쓰지 않습니다.
   - 노션에 없거나 미결정인 제품 판단(권한·경계값·문구 등 사용자가 체감하는 것)은 추정하지 않습니다. 사용자와 이번 범위에 필요한 판단을 끝까지 합의한 뒤 [기획 결정 요청](../../../docs/planning/README.md#plan-request)대로 Slack `#plan` 메시지 초안을 보여 주고, 확인받으면 게시합니다(Slack 도구가 없으면 본문만 출력). 사용자에게 보이지 않는 구현 판단(오류 코드·저장 방식)은 여기서 정합니다.
3. **코드 기준 확인**: [도메인 지도](../../../docs/domain/README.md)에서 대상 모듈을 찾고 그 경로의 `AGENTS.md`를 읽습니다. 대상 BC 문서(예: `docs/domain/schedule.md`)의 제품 규칙 참조·차이·공백에서 이번 작업에 걸린 차이 ID(`S-xx`)를 찾아 [대역별 구현 규칙](../../../docs/planning/README.md#gap-actions)을 적용합니다. 같은 모듈에서 가장 비슷한 기존 유즈케이스 하나(포트·서비스·테스트)를 골라 구조의 본보기로 삼습니다.
4. **PR 계획**: [PR 종류](../dino-pr/references/kinds.md#decide)와 [PR 단위](../dino-pr/references/planning.md#unit)로 나눕니다. 기본은 노션 기능 하나당 `유즈케이스` PR 하나입니다. 필요한 리팩터링은 선행 `구조 변경` PR로, 기존 계약을 깨는 변경은 `호환성 변경` 단계별 PR로 뺍니다.
5. **계획 파일**: 워크트리 루트 `<이슈키>-plan.md`(gitignore, 커밋하지 않음)에 아래 형식으로 씁니다.

   ```markdown
   # HM-000 <기능명> 계획
   - 기획 근거: <정책서 §절> / <기능명세 §절> (기획 버전 확인: <판정>)
   - 관련 차이: <S-xx와 대역> | 없음
   - 모듈: <module> (본보기: <비슷한 유즈케이스>)

   ## PR 1 — <종류>: <제목 초안>
   - 규칙: <명세에서 구현할 규칙 한 줄씩>
   - 차이: <해소하거나 새로 만드는 S-xx> | 없음
   - 선행: 없음 | PR n
   - 커밋: 1) <재현 테스트+구현 단위> 2) ...
   - 집중 검사: <테스트 클래스>
   - 문서: 없음 (모듈 책임·공개 계약·허용 의존성·모듈 공통 규칙이 바뀔 때만 해당 문서)
   - 완료 조건: <수용 기준>

   ## 기획 결정 요청 (노션 반영 대기)
   - <질문> — 합의안: <결정> · 대상: <문서 §절> · #plan: <메시지 링크>
   ```

6. **확인**: 계획 요약을 사용자에게 보이고 확인받은 뒤 구현합니다. `노션 반영 대기` 항목이 있으면 그 기능은 구현하지 않고 멈춥니다. 기획이 노션을 갱신한 뒤 사용자가 다시 요청하면 이 절차를 처음부터 다시 밟습니다. 구현은 `dino-architecture`와 `dino-testing`, 커밋은 `dino-commit`, 마무리는 `dino-pr` 스킬을 따릅니다.
