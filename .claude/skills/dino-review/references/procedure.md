# 리뷰 절차

리뷰는 PR을 올리기 전 로컬에서 개발자가 실행합니다. 한 번의 리뷰가 **비즈니스**(노션 명세 ↔ 코드 흐름)와 **기술**(컨벤션·모듈 계약·결함) 두 관점을 모두 보고, 결과는 [보고서와 마커](report.md#report)로 남깁니다. 리뷰 요청만으로 코드를 고치거나 PR·이슈에 게시하지 않습니다. [자동 검사와 리뷰의 역할](../../dino-testing/references/verification.md#evidence)에 따라 유효한 결과를 재사용하고 미검증 요구사항·영향·검사 자체의 적절성을 검토합니다.

## 범위

- PR 종류, 실제 base/head SHA, 커밋 순서를 확인합니다. 선행 PR 변경과 현재 diff를 구분하고 같은 SHA의 통계·검사 근거를 재사용합니다.
- PR 초안(`.claude/pr-drafts/`)과 계획 파일(워크트리 루트 `<이슈키>-plan.md`)이 있으면 기능 명세·핵심 다이어그램·구현 내용 표·관련 차이 ID를 가져옵니다.
- 리뷰는 커밋된 head를 대상으로 합니다. 커밋하지 않은 변경이 있으면 먼저 알리고, 마커는 커밋 뒤에만 남깁니다.

## 비즈니스 관점

노션 명세가 정한 동작이 코드 흐름에 그대로 구현됐는지 봅니다. 명세 자체가 옳은지는 판단하지 않습니다.

1. **대상 명세**: PR 초안 `## 기능 명세`나 계획 파일 `기획 근거`의 정책서·기능명세 절을 대상으로 합니다. 명세가 없는 종류(`유지보수`·`구조 변경`, 링크가 `없음`인 `결함 수정`·`호환성 변경`)는 `business: skip`과 이유를 적습니다.
2. **버전**: 세션의 [동기화 상태 확인](../../../../docs/planning/README.md#status) 결과를 재사용하고, 없으면 대상 문서만 확인합니다. PR이 인용한 버전보다 노션이 높으면 `버전 밀림`(판단 필요)입니다.
3. **규칙 목록**: 노션 본문은 하위 에이전트가 읽고 대상 절의 규칙만 넘깁니다(누가·무엇을·언제·거부 조건·결과). 노션을 읽지 못하면 레포의 절 참조·차이·공백까지만 판단하고 확인하지 못한 범위에 적습니다.
4. **규칙 추적**: 규칙마다 진입점(Controller·UseCase·리스너)부터 실제 코드 흐름을 따라가 구현 위치와 근거 테스트를 찾아 `trace`에 적습니다. 다르면 `명세 불일치`, 없으면 `명세 미구현`입니다. 다이어그램은 위치를 찾는 지도로만 쓰고 판정은 코드로 합니다.
5. **역방향**: 노션에 없는데 사용자가 체감하는 동작(권한·경계값·문구·조회 범위)을 코드가 정했으면 `명세 없음`(판단 필요)으로 적고 [기획 결정 요청](../../../../docs/planning/README.md#plan-request)을 요청합니다.
6. **차이 장부**: 구현 내용 표의 `차이` 열·`명세와 차이`가 실제 차이를 빠짐없이 적었는지, 해소·생성한 차이 ID가 BC 문서의 [차이·공백](../../../../docs/planning/README.md#gaps)에 반영됐는지 봅니다.

## 기술 관점

<a id="규약-검사"></a>
[PR 규약 검사](../../../../.github/scripts/check_pr_metadata.py)·Spotless·Checkstyle·테스트가 판정한 항목은 결과를 인용만 하고 다시 지적하지 않습니다. 로컬에서는 `pr_draft.py check`로 규약 검사 결과를 얻습니다.

1. **다이어그램과 표**: [핵심 다이어그램·구현 내용 표](../../dino-pr/references/kinds.md#절별-작성-기준)의 참여자·호출 순서·실패 분기가 코드와 같은지, 표의 근거 테스트가 실제로 그 규칙을 검증하는지 봅니다. 사람은 이것으로 판단하므로 다르면 `수정 필요`입니다.
2. **모듈 계약**: 변경에 해당하는 [모듈 경계](../../dino-architecture/references/architecture.md#modules)·[모듈 간 통신](../../dino-architecture/references/communication.md#communication)·[계층 의존](../../dino-architecture/references/architecture.md#layers)을 적용해 공개 타입·named interface·이벤트·`allowedDependencies`와 실제 호출부가 맞는지 확인합니다. 모듈 경계를 바꿨으면 `module-reviewer` 독립 검토 결과가 있는지 봅니다.
3. **결함**: 커밋 순서대로 구현·호출부·테스트를 따라 실패 경로·경계·널·동시성·상태 전이·트랜잭션·누락을 봅니다. 최종 상태 검사와 커밋별 근거를 구분하고, 발견은 위치·발생 조건·영향·근거를 갖추며 확정과 가설(`판단 필요`)을 나눕니다.
4. **컨벤션**: 의미 판단이 필요한 것만 봅니다(JPA·트랜잭션·이벤트·HTTP/DTO·테스트 설계). 기준은 `dino-architecture`·`dino-testing`의 references입니다.
5. **단위와 문서**: 선언한 PR 종류가 diff와 맞는지, 종류 혼합·다이어그램 3개 초과([PR 단위](../../dino-pr/references/planning.md#unit)), 커밋별 한 변경 이유, 소유 문서 갱신 누락, 검증 절이 실제 SHA·명령·결과를 담았는지 봅니다.

새 파일·삭제·이름 변경도 검토합니다. 생성물·잠금 파일·바이너리는 따로 표시하고, `numstat`에 줄 수가 없는 바이너리를 0줄로 보거나 큰 파일을 조용히 빼지 않습니다.

## 보고

[결과 파일](report.md#result)을 쓰고 HTML을 만든 뒤 개발자에게 보입니다. 검토한 커밋·범위와 확인하지 못한 범위를 적고, 일부 검토를 전체 완료로, 실행하지 않은 검사를 통과로 쓰지 않습니다. head가 바뀌면 새 diff와 영향받는 연결을 다시 확인합니다.
