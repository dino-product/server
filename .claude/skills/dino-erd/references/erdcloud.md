# ERDCloud 변경

팀 데이터 모델은 ERDCloud [Main ERD](https://www.erdcloud.com/d/3yXZhTYQ87poiJwTG)에 있습니다. 레포에 ERD를 복사하지 않고, 모듈 책임·설계 결정은 [BC 문서](../../../../docs/domain/bounded-contexts.md)가, 실제 스키마는 [영속성 규칙](../../dino-architecture/references/persistence.md)이 원본입니다. ERD 편집은 열려 있는 모든 사람에게 실시간으로 반영되는 공유 산출물 변경이므로 [게시 승인](../../dino-pr/references/publishing-approvals.md#publishing)을 따릅니다.

<a id="scope"></a>
## 범위

- 기본 범위는 작업 모듈이 소유한 테이블입니다. ERD의 색상 묶음(예: 작업 테이블은 초록)과 BC 문서의 소유 애그리게잇으로 소유를 판단하고, 다른 모듈 테이블의 컬럼·관계는 따로 합의한 경우에만 바꿉니다.
- 캔버스 메모는 팀의 설계 결정입니다. 예: "모듈 간 참조(schedule → organization)는 관계선 없이 논리 참조" 메모에 있는 컬럼에는 FK를 걸지 않습니다. 메모와 다르게 바꾸려면 메모 수정까지 합의합니다.
- 기준은 현재 ERDCloud 상태와 그날 합의한 결정입니다. 예전 계획 문서의 변경 목록을 그대로 적용하지 않습니다.

<a id="access"></a>
## 접근

- 편집은 ERDCloud MCP로 합니다. 등록 명령에 개인 토큰이 들어가므로 사용자가 ERD의 **AI Connect**에서 명령을 복사해 직접 실행합니다(`! claude mcp add …`). 에이전트는 토큰을 대화·파일에 옮기지 않습니다. 등록한 세션에는 도구가 로드되지 않아 세션을 다시 시작해야 합니다.
- 스냅샷 만들기와 SQL Preview 내보내기는 MCP에 없어 브라우저(Aside)로 합니다. `aside repl` 실행마다 연 탭이 닫히므로 열기·클릭·읽기를 한 번의 실행에 넣습니다.

<a id="mcp-behavior"></a>
## MCP 동작 특성

| 동작 | 결과 | 대응 |
| --- | --- | --- |
| `create_relation` | 기존 컬럼에 연결하지 않고 부모 PK 이름의 FK 컬럼(`id2` 등)을 맨 끝에 새로 만든다 | 새 컬럼 이름·NULL·코멘트를 원래대로 고치고 기존 컬럼을 지운다. 컬럼 순서는 바꿀 수 없어 맨 끝에 남는다고 미리 알린다 |
| `delete_relation` | 비식별 관계여도 FK 컬럼까지 지운다 | 컬럼을 남겨야 하면 같은 정의로 다시 추가한다 |
| `update_columns` | 여러 컬럼 수정을 한 번에 되돌릴 수 있는 단위로 적용한다 | 이름·타입·NULL·기본값 변경은 이것으로 묶는다. 삭제 후 추가 대신 기존 컬럼을 고쳐 위치를 유지한다 |
| 도메인 | 같은 도메인(`VARCHAR_NAME` 등)을 여러 테이블이 함께 쓴다 | 도메인 타입을 바꾸지 않고 해당 컬럼의 도메인만 바꾼다 |
| `list_tables` | 결과가 커서 잘린다 | 저장된 결과 파일에서 대상 테이블·컬럼 ID만 추린다 |

<a id="verify"></a>
## 확인

- 편집 전 ERDCloud **snapshot**을 만들고 SQL Preview를 기준선으로 저장합니다(MySQL, PK·FK·비식별 관계 제약 포함). 편집 뒤 같은 옵션으로 다시 받아 diff합니다. 옵션이 다르면 FK 구문이 통째로 빠져 비교가 틀립니다.
- diff에 합의한 항목만 있는지, 다른 모듈 테이블의 컬럼 정의·FK 수가 의도대로인지 확인하고 결과를 보고합니다. 조회 성공, 편집 실행, 저장 확인을 구분해 말합니다.
- SQL로 표현하지 못하는 제약(부분 유니크, 테이블 간 배타, 상태 전이)은 캔버스 메모로 남깁니다.
