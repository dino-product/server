# 작업 유형 선택

커밋·이슈·PR에서 변경 목적에 맞는 대표 유형을 선택할 때 읽습니다.

| 유형 | 선택 기준 |
| --- | --- |
| `feat` | 새로운 기능·API·외부 동작을 제공하는 작업 |
| `fix` | 기대 동작·합의된 계약과 다른 결과를 바로잡는 작업 |
| `docs` | 문서·설명·가이드만 바꾸는 작업. 실제 API 동작·계약도 변경하면 그 목적의 유형 사용 |
| `refactor` | 외부 동작을 보존하며 책임·의존성·코드 구조를 개선하는 작업 |
| `perf` | 응답 시간·처리량·자원 사용량의 개선이 주목적인 작업 |
| `test` | 테스트 자체나 테스트 환경의 개선이 주목적인 작업 |
| `build` | Gradle·패키징·의존성 변경이 주목적인 작업 |
| `ci` | CI 워크플로·자동 검사 실행 절차를 바꾸는 작업 |
| `chore` | 다른 유형에 속하지 않는 저장소 관리·보조 설정·유지보수 |
| `revert` | 특정 PR·커밋의 변경을 되돌리는 작업 |
| `investigation` | 불확실성을 해소하는 조사·질문·대안 비교와 결론 정리 |

대표 유형은 작업 목적을 기준으로 하나만 선택합니다. 버그 수정에 테스트·문서가 포함되어도 `fix`이고, 테스트만 보강하면 `test`입니다. `chore`로 분류하기 전에 더 구체적인 유형이 맞는지 확인합니다. 포맷만의 변경은 `chore`로 분류하고, 다른 작업에 수반된 포맷은 그 작업 유형을 따릅니다. 독립된 목적이 섞이면 이슈·PR을 나눕니다.
