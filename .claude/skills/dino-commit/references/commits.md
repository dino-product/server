# 브랜치·스테이징·커밋

권한은 [루트 작업 원칙](../../../../AGENTS.md#작업-원칙)을 따릅니다. 시작 시 worktree·staged diff를 확인하고 기본 브랜치를 원격 HEAD 등 실제 정보로 식별합니다. 수정 작업이 기본 브랜치에서 시작되면 사용 중이지 않은 작업 브랜치를 만듭니다. 식별할 수 없으면 추정하지 않습니다. 이름은 `<Jira-티켓번호>/<짧은-작업명>`을 기본으로 하되 팀·사용자 지정 이름이나 기존 작업 브랜치를 우선합니다.

- 이번 단위의 파일/hunk만 명시적으로 stage합니다. **staged diff 본문·경로를 확인한 뒤 별도 호출로 커밋**합니다. 다른 작업자의 변경·비밀값·생성물을 포함하지 않으며 소유권이 섞여 안전하게 분리할 수 없으면 커밋을 보류합니다.
- 제목은 `type(scope): 한국어 변경 요약`이고 `추가`, `차단`, `검증` 같은 명사형으로 끝냅니다. `~한다`형은 쓰지 않습니다. [유형](change-types.md#change-types)은 실제 목적, 선택적 scope는 실제 모듈·영역입니다. 예: `fix(auth): 다른 발급자의 Access Token 거부`.
- 호환성 파괴는 `type(scope)!: ...`와 본문의 깨지는 계약·전환 방법으로 표시합니다. 비단순 변경에는 문제·이유·실제 검증 근거를 적고, 제목만으로 이유가 명백하면 본문을 생략할 수 있습니다. 실제 관련 이슈만 연결하며 대화·실행 로그를 전재하지 않습니다.
- 실패·필수 집중 검사 미실행 단위는 커밋하지 않습니다. 중간 커밋 뒤 전체 검사 실패는 수정·검증한 새 커밋으로 보완합니다. 조사·리뷰만 요청받으면 임의 변경을 만들지 않고 명시된 커밋 금지를 지킵니다.
- 자동 이력 작업은 새 커밋 생성입니다. amend·rebase·reset·브랜치 삭제는 [Git 승인](git-approvals.md#git)을 따릅니다. 커밋 후 해시·목적·실제 검사 결과·남은 전체 검증을 보고합니다. 커밋은 푸시·PR 생성·병합 권한이 아닙니다.

## 구현 전 계획과 커밋 체크포인트

첫 편집 전 기능 목표와 예정 단위를 구분하고 각 단위의 한 변경 이유·파일/hunk·선행 의존성·집중 검사를 계획합니다. 계획은 대화나 임시 메모에 둡니다. 커밋은 고정 줄 수·파일 수가 아니라 사람이 한 이유를 이해·검증할 작은 단계입니다. 기능 작업은 [PR 계획](../../dino-pr/references/planning.md#planning) 안에서 커밋 순서를 정합니다.

1. 한 행동의 구현·필수 테스트·계약 문서를 함께 작성합니다. 파일·계층·구현/테스트별로 분리하지 않습니다. 동작 보존 준비 리팩터링이나 독립 문서·테스트 보강은 별도로 검토할 수 있으면 나눕니다.
2. 관련 집중 검사를 통과시키고 diff에서 선언·구현·호출부·테스트를 대조합니다. Web은 Request→Command/Query 변환과 Controller/Docs 시그니처·검증 선언, 모듈 간 변경은 공개 계약·소비자를 확인합니다. 문서 단위는 링크·경로·일관성과 `git diff --check`를 확인합니다.
3. 검증한 동작과 커밋할 파일/hunk를 일치시켜 즉시 커밋하고 다음 단위를 시작합니다. 부분 스테이징에서 제외한 구현 덕분에 통과했다면 커밋할 상태를 분리해 검사합니다. 커밋 금지 시에도 단위별 계획·검사·diff 검토 뒤 다음 단위로 이동합니다.
4. 모든 단위와 알려진 수정을 마치면 [전체 검증](../../../../AGENTS.md#검증과-완료)을 수행합니다. 새 문제는 수정·관련 검사 후 후속 커밋으로 남기고 최종 상태를 검증합니다.

별개 정책·책임 또는 별도 판단·검증이 필요하면 단위를 나눕니다. 묶어야 한다면 독립 검증·완결이 불가능한 이유를 계획에 적습니다. 각 커밋은 선행 커밋만으로 컴파일·관련 테스트·기동 조건을 충족해야 합니다. 의도한 실패 테스트는 구현과 함께 통과 상태로 커밋하며 분할을 위해 결합 코드를 삭제·재작성하거나 Bean 등록을 임시 제거하지 않습니다. 필수 집중 검사가 실패·미실행이면 해당 커밋과 범위 확대를 보류하고 삭제 없는 진단·수정을 계속합니다. 독립 단위는 별도 작업 트리를 사용합니다. 중간 집중 검사를 전체 통과로 보고하지 않습니다. 커밋 분리와 PR 분리는 각각 판단하며 여러 커밋으로 한 PR에 독립 목적을 누적하지 않습니다.

참고: [Git의 논리적 변경 분리](https://git-scm.com/docs/SubmittingPatches), [Linux의 중간 상태 조건](https://docs.kernel.org/process/submitting-patches.html#separate-your-changes).
