# Schedule 모듈 지침

[루트 지침](../../../../../../AGENTS.md)에 추가 적용합니다. 책임·애그리게잇은 [schedule 문서](../../../../../../docs/domain/schedule.md#schedule), 제품 규칙(권한·시간 제한·사유 목록 등)은 [기획 원본 색인](../../../../../../docs/planning/README.md#planning)의 Notion 정책서와 [제품 규칙 참조](../../../../../../docs/domain/schedule.md#schedule-product), 구현 규칙은 [구현 결정](../../../../../../docs/domain/schedule.md#schedule-implementation)이 원본입니다. 여기에 타입 목록·전이표·제품 규칙을 복제하지 않습니다.

- [차이·공백](../../../../../../docs/domain/schedule.md#schedule-gaps)의 항목은 [대역별 구현 규칙](../../../../../../docs/planning/README.md#gap-actions)대로 다룹니다. `S-0x`·`S-2x`는 요청받으면 Notion 기준으로 해소하고, `S-1x`·`S-3x`는 Notion 결정 전에 구현하지 않습니다. 구현 중 사용자가 체감하는 새 판단이 필요하면 `S-1x`로 적고 [기획 결정 요청](../../../../../../docs/planning/README.md#plan-request)을 합니다.
- `domain`, `application`, `adapter/in/web`, `adapter/in/organization`, `adapter/in/profile`, `adapter/in/event`, `adapter/out`이 있고 구현 범위는 [도메인 지도](../../../../../../docs/domain/README.md#모듈별-책임과-공개-계약)가 원본입니다. 모듈 루트 공개 계약은 작업 이벤트 record(`WorkAssigned` 등, 소비자 notification)이고, organization이 선언한 요구 인터페이스 `TechnicianWorkRelease`·`WorkTypeRelease`를 `adapter/in/organization`이, profile이 선언한 요구 인터페이스 `WithdrawalBlocker`를 `adapter/in/profile`이 구현해 입력 포트로 넘깁니다. `TechnicianWorkRelease` 구현은 결과와 기사 일정 대기 초과(`SCHEDULE-006`)를 계약의 타입·예외(`TechnicianWorkReleaseBusyException`)로 옮깁니다. profile 이벤트 `AccountWithdrawn`은 `adapter/in/event`가 구독합니다. `allowedDependencies`는 `shared::error`, `shared::openapi`, `shared::persistence`, `organization`, `auth`, `profile`입니다.
- 웹 어댑터는 요청자 계정을 auth의 루트 공개 계약 `AccountPrincipal`로 받아 계정 식별자만 Command에 넘깁니다. 식별자 형식·작업명 길이 같은 입력 규칙은 서비스·도메인이 한 번만 검사해 아래 오류 순서를 지키므로, Request·경로 값에 같은 Bean Validation 제약을 두지 않습니다. 웹 계층은 인증 실패(401)와 숫자가 아닌 경로 식별자·깨진 본문·목록에 없는 값·형식이 틀린 쿼리 값(시각·숫자, 400 `COMMON-400`)만 서비스보다 먼저 거릅니다. 조회 구간처럼 서비스가 확인 순서를 지켜야 하는 쿼리 값은 필수로 두지 않고 서비스가 확인합니다.
- 요청자는 `adapter/out/organization/OrganizationActorAdapter`가 organization의 `OrganizationMemberLookup`으로 찾아 `Actor`로 옮깁니다(ACL). 기사 계약은 같은 패키지의 `OrganizationTechnicianContractAdapter`(배정 대상 확인)와 `OrganizationAccountTechnicianContractsAdapter`(계정의 기사 계약 목록)가 organization의 `TechnicianContractLookup`으로 옮깁니다. 포트마다 어댑터를 나눠, 테스트가 한 포트만 `@MockitoBean`으로 바꿔도 다른 포트의 구현이 남게 합니다. 서비스는 organization 타입을 직접 주입하지 않고 ACL 출력 포트(`LoadActorPort`·`TechnicianContractPort`·`WorkTypePort`·`AccountTechnicianContractsPort`, 조회 화면의 표시 정보인 `LoadTechnicianProfilesPort`·`LoadStaffProfilesPort`·`LoadWorkTypeLabelsPort`)만 씁니다.
- 작업이 참조하는 조직 자원은 서비스가 `OrganizationReferences`로 확인합니다. 배정·재배정의 담당기사는 `TechnicianContractPort`로 그 조직의 활성 기사 계약인지 봅니다. 담당기사는 `ScheduleChanges`에서 기사를 잠근 직후 확인해, 같은 기사를 잠그고 배정을 푸는 대기함 반환과 한 줄로 섭니다. 그래서 `TechnicianWorkRelease` 구현(`ReleaseTechnicianWorksService`)도 같은 기사 잠금을 거칩니다. 등록·기본정보 수정의 작업 유형은 `WorkTypePort`로 그 조직에서 선택할 수 있는 유형인지 봅니다(유형을 비우면 확인하지 않고, 기본정보 수정은 유형이 바뀔 때만). 일정 변경은 현재 담당기사를 다시 확인하지 않습니다. 기사 비활성화·역할 변경은 대기함 반환으로 배정을 풀기 때문입니다. 탈퇴는 이 계약 밖이며, profile 요구 인터페이스 `WithdrawalBlocker` 구현(차단 조건은 [조직·계정] §5.1)과 `AccountWithdrawn` 구독(배정됨·작업전 반환)으로 처리합니다(HM-320). 그래서 탈퇴한 기사에게 남는 작업은 주로 작업중 작업이고(반환 전 틈과 남는 위험은 [schedule 문서의 동시성](../../../../../../docs/domain/schedule.md#schedule-implementation)), 그 작업의 일정 변경은 담당기사를 다시 확인하지 않습니다. 판정 구현(`adapter/in/profile/WithdrawalBlockerAdapter`)은 `GetWithdrawalBlockingWorksUseCase`를, 구독(`adapter/in/event/AccountWithdrawnListener`)은 `ReleaseWithdrawnTechnicianWorksUseCase`를 부릅니다. 리스너는 `@ApplicationModuleListener(propagation = NOT_SUPPORTED)`로 자체 트랜잭션 없이 두어, 기사를 잠그는 반환 유즈케이스가 READ COMMITTED 트랜잭션을 직접 시작하게 합니다.
- 컨트롤러(`adapter/in/web`)는 임시 어댑터에 기대는 유즈케이스까지 만들 수 있습니다. 임시 어댑터가 `local`·`test`·`dev`에서만 등록돼 운영(`prod`)과 프로필 없는 실행은 기동하지 않으므로, 실제 계약 연결 전까지 운영에는 노출되지 않습니다([제공 기능이 아직 없을 때](../../../../../../.claude/skills/dino-architecture/references/communication.md#제공-기능이-아직-없을-때)). `local`·`dev`에서는 임시 어댑터의 거부·빈 결과대로만 동작합니다.
- Work 저장소와 목록 조회는 `adapter/out/persistence`의 JPA 어댑터(`WorkPersistenceAdapter`·`WorkQueryPersistenceAdapter`, 모든 프로필 등록)입니다. 테이블은 팀 ERD의 작업 테이블을 따르고 매핑 규칙은 [JPA 모델](../../../../../../.claude/skills/dino-architecture/references/persistence.md#jpa), 이 모듈의 매핑 결정은 `WorkMapper` Javadoc이 원본입니다. 그 밖의 출력 포트 구현은 임시입니다: 조회 화면의 표시 정보를 찾는 `adapter/out/organization/EmptyTechnicianProfilesAdapter`(활성 기사 목록·기사 이름·기사유형)·`EmptyStaffProfilesAdapter`(등록자 이름·직원유형)·`EmptyWorkTypeLabelsAdapter`(작업유형 이름·색)는 빈 결과를 돌려주며, organization의 기사 계약·소속·유형 조회 계약(HM-288·HM-291·HM-295)과 profile의 계정 이름 조회 계약(HM-305)이 생기면 둘을 합쳐 호출하는 어댑터로(기사·등록자는 organization 계약이 주체라 `adapter/out/organization`에 두고 이름만 profile 계약으로 채움), `adapter/out/storage/FakePhotoUrlAdapter`(식별자를 붙인 가짜 주소)는 사진 업로드 방식이 정해지면(HM-238) 실제 저장소 어댑터로 교체한 뒤 삭제합니다. `adapter/out/organization/DenyingWorkTypeAdapter`(모든 작업 유형을 거부, HM-295 전에는 유형이 없음)는 organization이 작업 유형 확인 공개 계약(HM-295)을 제공하면 그 계약을 호출하는 어댑터로 교체한 뒤 삭제합니다. 그 전까지 `local`·`dev`에서는 유형을 지정한 등록·수정이 `SCHEDULE-014`로 거부됩니다. 임시 구현은 `local`·`test`·`dev` 프로필에서만 등록합니다. 이 포트를 쓰는 서비스가 있으므로 현재 그 밖의 프로필(`prod`, 프로필 없음)은 Bean 부재로 기동하지 않으며, 이것이 의도입니다. 실제 어댑터를 추가하고 임시 구현을 지우지 않으면 Bean 중복으로 실패하니 `@Primary`로 덮지 않습니다.
- `WorkRepository`의 조회 사본 계약은 [JPA 모델의 조회 결과 규칙](../../../../../../.claude/skills/dino-architecture/references/persistence.md#jpa)을 따릅니다. 이 모듈에서는 배정·재배정·일정 변경이 미확인 겹침일 때 `save`를 생략하는 판정이 그 계약에 기댑니다.
- 기사 일정을 차지하거나 옮기는 유즈케이스(배정·재배정·일정 변경, 이를 한 요청으로 고르는 배정 변경 `ChangeWorkAssignmentService`, 일정을 함께 준 등록 `CreateWorkService`)는 `ScheduleChanges`를 거칩니다. 기사의 활성 작업을 읽어 판정하는 다른 유즈케이스(역할 변경·비활성화·탈퇴의 대기함 반환)도 읽기 전에 `TechnicianScheduleLocks`로 같은 기사를 잠급니다. 기사 요청(수락·거절·시작)은 기사의 다른 작업을 읽지 않지만, 같은 기사를 잠그는 대기함 반환·일정 변경·같은 작업의 중복 요청과 한 줄로 서도록 작업 식별자 형식을 확인한 직후, 작업을 읽기 전에 같은 기사를 잠급니다(먼저 읽으면 영속성 컨텍스트의 낡은 작업을 써서 버전 충돌이 납니다). 완료보고는 반환이 바꾸는 작업(배정됨·작업전)을 건드리지 않아 잠그지 않습니다. 일정 일부만 준 등록도 미리 입력한 담당기사를 잠근 뒤 확인합니다. 대기함 반환이 같은 잠금 안에서 그 기사를 가리키는 미리 입력한 담당기사를 비우므로([스케줄·배정] §9), 잠그지 않으면 반환과 동시에 등록한 작업이 비활성·탈퇴한 기사를 가리킨 채 남습니다. 잠금으로 같은 기사를 동시에 바꾸는 요청을 한 줄로 세웁니다. 한 트랜잭션에서 여러 기사를 잠그는 유즈케이스(탈퇴 반환 `ReleaseWithdrawnTechnicianWorksService`)는 교착을 피하도록 조직 ID·기사 계약 ID 오름차순으로 잠급니다. 구현(`PostgresTechnicianScheduleLockAdapter`)은 PostgreSQL 트랜잭션 advisory lock이라 임시 어댑터와 달리 모든 프로필에서 등록되고, 저장소와 같은 트랜잭션 연결에서만 동작합니다. 대기 한도는 `app.schedule.technician-lock.wait-limit`(기본 2초)입니다.
- 잠금은 잠근 뒤의 조회가 앞선 커밋을 볼 때만 유효합니다. 기사를 잠그는 서비스는 `@Transactional(isolation = Isolation.READ_COMMITTED)`를 명시하고 `TechnicianScheduleLockIsolationTest`가 이를 확인합니다. 이 설정은 그 서비스가 트랜잭션을 시작할 때만 적용되고 바깥 트랜잭션에 참여하면 무시되므로, 잠그는 서비스를 다른 트랜잭션 안에서 호출하지 않습니다. 예외는 organization 트랜잭션과 함께 커밋해야 하는 대기함 반환(`ReleaseTechnicianWorksService`)으로, `propagation = MANDATORY`로 바깥 트랜잭션을 요구하고 격리 수준은 PostgreSQL 기본값(READ COMMITTED)에 기대며 바깥이 그보다 높은 격리 수준을 지정했으면 잠그기 전에 거부합니다. 격리 테스트는 이 서비스를 이름으로 따로 확인합니다. 기사 일정 잠금(advisory lock)을 잡은 뒤에는 organization의 발주사·소속 행을 잠그지 않습니다. organization은 자기 행을 잠근 트랜잭션에서 대기함 반환을 불러 기사 일정 잠금을 잡을 수 있으므로, 반대 순서가 생기면 교착됩니다. JPA 어댑터는 기사 활성 작업 조회에 쿼리 캐시·2차 캐시를 쓰지 않습니다. 잠그기 전에 같은 기사의 다른 작업을 영속성 컨텍스트에 올려 두면 잠근 뒤 조회가 그 오래된 인스턴스를 돌려주므로, 잠금 전에는 대상 작업만 읽습니다.
- 도메인 불변식 예외는 서비스가 `DomainRuleViolations`로 감싸 오류 코드로 바꿉니다. 람다에는 도메인 호출만 넣습니다. 요청자의 입력이 아닌 다른 모듈의 처리 안에서 일어나는 변경(`ReleaseTechnicianWorksService`의 대기함 반환, `ReleaseWithdrawnTechnicianWorksService`의 탈퇴 반환)은 감싸지 않아 500으로 둡니다.
- 작업 이벤트는 일어난 사실이며, 변경 유즈케이스가 저장한 뒤에만 `ApplicationEventPublisher`로 발행합니다(겹침 미확인 보류·중복 요청·거부면 발행하지 않음). 누구에게 알릴지는 담지 않고 구독하는 쪽이 정합니다. 이벤트는 `WorkEvents`의 팩터리로 만들고, 어떤 사실인지(대기함 배정·재배정·일정 변경)와 취소 당시 담당 기사를 고르려고 변경 전 상태와 담당 기사를 변경 전에 잡아 둡니다. 일정을 함께 준 등록은 저장소가 돌려준 작업으로 만듭니다(식별자가 저장 뒤에 생김). 발행 규칙은 [구현 결정](../../../../../../docs/domain/schedule.md#schedule-implementation)의 작업 이벤트가 원본입니다. 서비스 테스트는 `RecordingEventPublisher`로 발행·미발행을 확인합니다(`assertRejected`·`assertRejectedWithoutSaving`이 미발행도 확인).
- Domain은 Spring·JPA·Web 타입과 `Clock`에 의존하지 않습니다. 시각은 호출자가 UTC `Instant`로 넘깁니다.
- 상태는 업무별 메서드로만 바꾸고 상태만 주입하는 경로를 두지 않습니다. 새 전이는 Notion 기준을 확인한 뒤 구현 결정 절과 전이 규칙·테스트를 함께 바꿉니다.
- 배정 이력은 추가만 합니다. 수락·거절로 확정된 결과는 바꾸지 않고 현재 배정은 최신 이력입니다. 관리자 조치로 끝난 배정에는 종료 기록(`AssignmentEnding`)만 더합니다. 저장값 복원도 결과·시각·사유·종료 기록의 정합성을 검증하므로, JPA 저장에는 배정자와 종료(시각·처리자·방식), 작업의 시작·완료 시각과 취소 기록(시각·처리자·사유·메모)을 모두 담습니다.
- 조직과 조직이 소유한 소속·기사 계약·작업 유형은 ID 값객체로만 참조합니다. 관리자(조직 소속)와 기사(기사 계약)는 서로 다른 ID로 참조합니다.

## 오류 순서

HTTP 요청은 웹 계층이 먼저 인증 실패(401)와 숫자가 아닌 경로 식별자·깨진 본문·목록에 없는 값·형식이 틀린 쿼리 값(400 `COMMON-400`)을 거르고, 그 뒤 모든 변경 유즈케이스는 아래 순서로 확인해 먼저 걸린 오류 하나만 돌려줍니다. 서비스 javadoc은 이 순서를 복제하지 않고 자기 유즈케이스의 규칙만 적습니다.

1. 계정 식별자 누락 — 인증 계층의 프로그래밍 오류(500)
2. 조직 식별자 형식 — 400 `SCHEDULE-003`
3. 조직의 활성 관리자(소속)도 기사(기사 계약)도 아님 — 403 `SCHEDULE-004`, 유즈케이스의 요청자 종류가 아님(관리 유즈케이스에 기사, 기사 유즈케이스에 관리자) — 403 `SCHEDULE-005`
4. 작업 식별자 형식 — 400 `SCHEDULE-003`, 없거나 다른 조직의 작업 — 404 `SCHEDULE-001`
   - 4-1. 관리자 변경 유즈케이스 중 등록자 본인·총관리자만 하는 변경(기본정보 수정·취소·배정 해제, 대기함이 아닌 작업의 배정 변경·재배정·일정 변경)을 다른 직원이 요청함 — 403 `SCHEDULE-005`. 조회·기사 유즈케이스와 대기함 작업의 배정에는 없음
   - 4-2. 배정 변경·배정 해제에서 요청자가 본 버전이 없거나 음수 — 400 `SCHEDULE-003`, 지금 버전과 다름 — 409 `SCHEDULE-016`
5. 요청 값 형식(작업명·금액·기사·시간 등) — 400 `SCHEDULE-003`
6. 현재 상태로 할 수 없음 — 409 `SCHEDULE-002`
7. 현재 값과 같음(같은 기사 재배정 409 `SCHEDULE-007`, 같은 시간 일정 변경 409 `SCHEDULE-008`), 배정 이력·등록 시각 역전 400 `SCHEDULE-003`. 완료보고 요청은 6번(작업중이 아니거나 예정 종료 전 409 `SCHEDULE-002`)과 시각 역전(400) 뒤에, 같은 작업의 마지막 요청 뒤 30분이 지나지 않았으면 429 `SCHEDULE-019`
8. 지정한 작업 유형을 그 조직에서 선택할 수 없음(등록, 유형을 바꾸는 기본정보 수정) — 400 `SCHEDULE-014`. 다른 조직의 유형과 없는 유형을 구분하지 않음
9. 같은 기사의 앞선 변경을 기다리다 대기 한도 초과 — 409 `SCHEDULE-006`. 이어서 배정·재배정은 고른 담당기사가 그 조직의 활성 기사 계약이 아니면 400 `SCHEDULE-013`(일정 일부만 준 등록의 미리 입력한 담당기사도 같은 기사를 잠근 뒤 확인). 기사도 다른 조직의 계약과 없는 계약을 구분하지 않음
10. 일정 겹침 — 확인하지 않은 요청은 반영하지 않고 겹친 작업을 돌려줌(오류 아님)
11. 반영할 때 저장 자리에서 다른 트랜잭션이 이 작업을 먼저 바꾼 것이 드러남 — 배정 변경·배정 해제와 배정·재배정·일정 변경, 완료보고 요청은 409 `SCHEDULE-016`, 그 밖의 변경은 아직 500(HM-236)

기사가 요청하는 유즈케이스(수락·거절·시작·완료보고)는 3번의 요청자가 기사입니다. 수락·거절·시작은 4번의 작업 식별자 형식 뒤 작업을 찾기 전에 기사를 잠가, 대기 한도를 넘기면 409 `SCHEDULE-006`입니다(완료보고는 잠그지 않음). 4번의 작업 조회 뒤에는 다음을 확인합니다.

- 기사가 볼 수 없는 작업(작업에 남은 일정의 기사가 아님: 배정받은 적 없음·거절함·다른 기사로 재배정됨·배정 해제·반환됨) — 404 `SCHEDULE-001`(다른 조직 작업처럼 존재를 숨김)
- 요청 값 형식(배정 순번, 거절 사유·메모, 완료보고 등) — 400 `SCHEDULE-003`
- 기사가 본 순번의 배정이 없거나 요청한 기사의 배정이 아님 — 403 `SCHEDULE-009`
- 그 배정이 이미 최신이 아님(그 사이 일정 변경, 다른 기사나 대기함을 거쳐 다시 배정됨) — 409 `SCHEDULE-010`
- 최신 배정이 그 요청을 처리할 수 있는 상태가 아님 — 409 `SCHEDULE-002`. 단 같은 기사가 같은 배정에 이미 같은 요청(수락, 시작, 같은 내용의 완료보고)을 했고 그 배정이 그대로면 아무것도 바꾸지 않고 성공한다(중복 전송)
- 요청 시각이 앞선 기록(배정·수락·시작 시각)보다 앞섬(서버 간 시계 차이) — 400 `SCHEDULE-003`, 관리자 유즈케이스의 이력 시각 역전과 같은 분류
- 시작만: 마지막으로 그 배정 일정의 시작 가능 시간(예정 시작 10분 전)보다 이르면 409 `SCHEDULE-017`, 예정 종료 시각이 지났으면 409 `SCHEDULE-018`. 같은 기사의 다른 작업이 작업중이어도 막지 않는다

조회 유즈케이스도 1~4번을 같은 순서로 확인하고, 요청자가 기사면 4번 뒤 기사가 볼 수 없는 작업일 때 404 `SCHEDULE-001`입니다. 완료보고 조회는 이어서 보고가 없으면 404 `SCHEDULE-012`입니다. 작업 식별자 없이 기간·조건으로 모아 보는 조회는 3번 뒤에 구간·검색 조건을 확인합니다(400 `SCHEDULE-003`). 기사를 대상으로 하는 조회(작업 이력)는 3번 뒤 기사 식별자(관리자는 필수, 형식 400) → 기사가 다른 기사를 지정하면 403 `SCHEDULE-005`(요청자 종류가 아니라 대상 불일치에도 씀) → 구간 순서이며, 기사 본인이 조회하면 본인이 완료한 작업만 담습니다. 조회는 저장하지 않으므로 `@Transactional(readOnly = true)`로 두고, 여러 번 읽어 한 화면을 만드는 조회(타임테이블의 칸·대기함 등)는 같은 시점을 보도록 `isolation = Isolation.REPEATABLE_READ`를 더하고 `SnapshotQueryIsolationTest`가 이를 확인합니다.

배정 순번은 배정 이력의 1부터 시작하는 위치입니다. 이력은 추가만 되므로 순번은 바뀌지 않습니다.

## 다음 작업에 넘길 것

- HM-295 후속(작업 유형·표시 정보 어댑터 교체): organization 공개 계약 `WorkTypeLookup`·`MemberDirectory`가 생겼습니다. `DenyingWorkTypeAdapter`는 `WorkTypeLookup#isSelectable`을, `EmptyWorkTypeLabelsAdapter`는 `WorkTypeLookup#findLabels`를, `EmptyStaffProfilesAdapter`·`EmptyTechnicianProfilesAdapter`는 `MemberDirectory`와 profile 이름 조회(HM-305)를 부르는 어댑터로 바꾸고 임시 어댑터를 지웁니다(S-25도 이때 해소). `isSelectable`은 유형 행을 공유 잠금으로 잡으므로 작업 저장과 같은 읽기·쓰기 트랜잭션에서, 작업 행을 바꾸기(flush) 전에 부릅니다(지금 `OrganizationReferences` 호출 위치가 이 순서입니다). 작업중부터 유형 고정과 "유형이 바뀔 때만 확인"은 이미 구현해, 삭제된 유형을 가진 작업중 작업도 지금 유형을 그대로 보내면 다른 항목을 고칠 수 있습니다. 유형 삭제의 건수·시작 전 작업 해제는 organization 요구 인터페이스 `WorkTypeRelease`의 구현(`adapter/in/organization/WorkTypeReleaseAdapter`, `CountWorksByTypeService`·`ReleaseDeletedWorkTypeService`)이 맡으며, 해제는 작업을 읽지 않고 한 문장으로 바꿔 버전을 올립니다.
- HM-236(버전 충돌): 배정 변경·배정 해제는 요청자가 본 버전(`expectedVersion`)을 받아 비교하고, 어댑터 `save`가 flush해 저장 자리의 버전 충돌을 `ConcurrentWorkChangeException`으로 알리며 두 경우 모두 409 `SCHEDULE-016`입니다(`WorkVersions`). 나머지 유즈케이스(기본정보 수정·취소·기사 요청·반환)는 저장 자리의 충돌을 아직 변환하지 않아 500입니다. 기사 요청(수락·거절·시작)이 기사 잠금으로 한 줄로 서는 경합(대기함 반환·일정 변경·같은 작업의 중복 요청)은 뒤에 온 쪽이 앞선 커밋을 보고 판정해 기사 요청 쪽에서는 버전 충돌이 나지 않으므로(일정 변경이 늦으면 일정 변경 쪽이 `SCHEDULE-016`) 재실행 대상이 아니고, 남는 충돌은 같은 기사를 잠그지 않는 재배정(새 담당기사만 잠금)·배정 해제·취소·기본정보 수정과의 경합과 잠그지 않는 완료보고의 경합(취소·기본정보 수정·완료보고 요청·같은 보고의 중복 전송)입니다. 웹에 노출하지 않은 배정·재배정·일정 변경 입력 포트는 본 버전을 받지 않습니다. 기본정보 수정은 [작업] §5대로 나중 저장이 이기므로 본 버전을 받지 않습니다. 기사 쪽 요청이 충돌하면 새 트랜잭션에서 유즈케이스를 한 번 다시 실행해 다시 읽은 상태로 결과를 정합니다(재배정·배정 해제에 졌으면 볼 수 없는 작업이라 404 `SCHEDULE-001`, 취소에 졌으면 `SCHEDULE-002`, 기본정보 수정에 졌으면 상태·배정이 그대로라 충돌이 없던 것처럼 처리, 완료보고가 같은 보고의 중복 전송에 졌으면 성공). 두 트랜잭션으로 확인하는 통합 테스트를 둡니다: 재배정 대 수락, 재배정 대 시작, 같은 작업의 완료보고 두 건(시작 두 건은 기사 잠금으로 한 줄로 서 뒤 요청이 재실행 없이 중복 전송 성공), 같은 기사를 동시에 배정할 때 뒤 요청이 앞 요청의 커밋을 보고 겹침을 돌려주는 경우. 배정 순번은 ERD에 순번 컬럼이 없어 `id` 순(IDENTITY 삽입 순)에 기대고 있으며, 순번 컬럼 추가는 ERD 제안으로 남깁니다. 시작시각은 범위 제한이 없어 PostgreSQL `timestamptz`가 받지 못하는 먼 연도가 들어오면 저장 때 500이 나므로 허용 범위를 정해 도메인이나 API에서 막습니다. 입력 정책을 좁힐 때는 저장된 데이터의 복원 검증 실패를 막기 위해 기존 데이터를 옮기거나 복원 검증을 구조 검증으로 한정합니다.
- HM-238(API): 반영하지 않은 겹침 결과는 HM-217에서 200 `{applied=false, conflicts}`로 공개했습니다. 확인 뒤 새로 생긴 겹침도 허용할지(지금은 허용) 정합니다. 재시도 처리도 정합니다: 일정을 준 등록은 겹침을 확인하지 않으면 작업을 만들지 않지만 일정 없는 등록이나 확인 뒤 재시도는 중복 생성되고, 이미 반영된 배정·해제·취소를 다시 보내면 상태 오류(`SCHEDULE-002`)라 '이미 처리됨'과 '다른 사람이 먼저 바꿈'을 구분하지 못합니다(수락·시작·완료보고의 같은 요청 재전송은 이미 성공으로 처리하고, 거절 재전송은 볼 수 없는 작업이라 404입니다). 사용자 안내 기준은 [스케줄·배정] §7(SCH-006)이며, 배정 변경·해제는 본 버전 비교(409 `SCHEDULE-016`)로 '다른 사람이 먼저 바꿈'을 따로 알립니다. 기사 화면의 작업 조회 응답에는 수락·거절·시작·완료보고에 쓸 배정 순번을 담습니다. 완료보고 사진과 현장 사진(HM-330)은 모두 업로드를 먼저 마친 파일의 식별자로 받으므로, 업로드 방식과 식별자 형식·이미지 여부 검증(S-06)을 이때 두 사진에 함께 정합니다. 식별자 길이 상한은 지금 현장 사진(`Work.MAX_SITE_PHOTO_ID_LENGTH`, 빈 값 거부)에만 있고 완료보고 사진에는 없어 `work_execution_images.image_url`(500)을 넘치면 커밋 때 500이므로, 같은 검증을 완료보고 사진에도 둡니다. 조회 응답의 사진 주소(`PhotoUrlPort`)도 형식·만료·접근 권한을 정해 실제 저장소 어댑터로 구현합니다. 지금은 사진 한 장마다 주소를 만들므로(관리자 상세는 완료보고 사진과 현장 사진 최대 6장까지), 서명 URL처럼 왕복이 드는 저장소라면 여러 장을 한 번에 바꾸는 일괄 변환을 함께 정합니다.
- HM-347(운영 DB 전환): `work.status` 값이 `PENDING_ACCEPTANCE`→`PENDING_ACCEPT`, `CANCELLED`→`CANCELED`로 바뀌었습니다. 마이그레이션 도구가 없고 `ddl-auto: none`이라 직접 바꿉니다. 옛 앱을 멈춘 뒤 새 앱을 띄우기 전에, Hibernate가 만든 enum check 제약(`status in (...)`)이 있으면 그 제약을 지우고, 저장된 값을 `UPDATE`로 바꾼 뒤, 새 값 목록으로 제약을 다시 추가합니다(PostgreSQL은 제약을 추가할 때 기존 행을 검사함).
