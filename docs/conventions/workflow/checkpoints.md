# 구현 전 계획과 커밋 체크포인트

작업 단위 계획·첫 편집 전에 읽습니다. 커밋은 사람이 한 변경 이유를 이해·검증할 작은 단계이며, 기능 전체나 고정 줄 수·파일 수·개수를 단위로 삼지 않습니다. 기능 작업은 [PR 계획](pull-requests/planning.md#planning) 안에서 커밋 순서를 정합니다.

1. **계획:** 전체 기능 목표와 예정 단위를 구분하고, 각 단위의 한 변경 이유·파일/hunk·선행 의존성·집중 검사 명령을 나열합니다. 문서 단위는 링크·경로·일관성과 `git diff --check`를 검사합니다. 계획은 대화나 임시 메모에만 둡니다.
2. **한 단위 구현:** 이번 단위의 한 행동에 필요한 구현·필수 테스트·계약 문서를 함께 작성합니다. 파일·계층·구현/테스트별로 나누지 않습니다. 동작을 보존하는 준비 리팩터링이나 독립 문서·테스트 보강도 한 이유로 검토할 수 있으면 분리합니다.
3. **검증·계약 대조:** 관련 집중 검사를 통과시키고 diff를 검토합니다. 해당 계약의 선언·구현·호출부·테스트를 함께 확인합니다. Web은 Request→Command/Query 변환과 Controller/Docs 시그니처·검증 선언, 모듈 간 변경은 공개 계약·소비자를 대조합니다.
4. **즉시 커밋:** [스테이징·커밋](commits.md#commits)을 마친 뒤 같은 작업 트리에서 다음 단위를 시작합니다. 여러 책임을 모두 구현한 뒤 일괄 커밋하거나 마지막에만 이력을 나누지 않습니다. 해시·목적·실제 검사 결과를 짧게 보고합니다. 커밋 금지 시에도 단위별 계획·검사·diff 검토를 마친 뒤 다음 단위로 이동하며 Git 기록만 생략합니다.
5. **완료 검사:** 모든 단위와 알려진 수정을 마치면 [루트 전체 검증](../../../AGENTS.md#검증과-완료)을 수행합니다. 새로 발견한 문제는 수정·관련 검사 후 후속 커밋으로 남기고 최종 상태에 필요한 전체 검증을 마칩니다. 문서 전용 예외·커밋 금지 요청은 그대로 적용합니다.

- 별개 정책·책임이나 별도의 판단·검증이 필요하면 나눕니다. 묶어야 한다면 독립 검증·완결이 불가능한 이유를 계획에 적습니다. 유스케이스 연결만으로 한 커밋에 묶거나 PR 줄 수까지 누적하지 않습니다.
- 각 상태는 선행 커밋만으로 컴파일·관련 테스트·기동 조건을 충족해야 합니다. 후속 구현에 의존하는 실패 상태를 남기지 않습니다. 의도한 테스트 실패는 구현과 함께 통과 상태로 커밋합니다. 분할하려고 결합 코드를 삭제·재작성하거나 Bean 등록을 임시 제거하지 않습니다.
- 검증한 상태와 커밋할 파일/hunk의 동작을 일치시킵니다. 부분 스테이징에서 제외한 구현 덕분에 검사가 통과했다면 커밋할 상태를 분리해 검사합니다.
- 필수 집중 검사가 실패·미실행이면 그 단위의 커밋과 범위 확대를 보류합니다. 삭제 없는 진단·수정은 계속하고 독립 단위가 필요하면 별도 작업 트리를 사용합니다. 중간 검사 통과를 전체 검증 완료로 보고하거나 필요한 검사를 횟수 제한으로 생략하지 않습니다.
- 커밋과 PR의 분리는 각각 확인합니다. 여러 커밋이어도 독립 목적을 한 PR에 누적하지 않습니다.

참고 근거: [Git의 논리적 변경 분리](https://git-scm.com/docs/SubmittingPatches), [Linux의 중간 상태 조건](https://docs.kernel.org/process/submitting-patches.html#separate-your-changes).
