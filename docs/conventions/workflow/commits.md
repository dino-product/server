# 브랜치·스테이징·커밋

커밋 시 읽습니다. 변경 단위와 검사 조건은 먼저 적용한 [체크포인트](checkpoints.md#checkpoints), 권한은 [루트 작업 원칙](../../../AGENTS.md#작업-원칙)을 따릅니다.

- 시작 시 worktree·staged diff를 확인합니다. 기본 브랜치는 원격 HEAD 등 실제 정보로 식별하고, 수정 작업이면 사용 중이지 않은 작업 브랜치를 먼저 생성합니다. 식별할 수 없으면 추정하지 않습니다.
- 브랜치는 `<type>/<짧은-작업명>`을 기본으로 하되 팀·사용자 지정 이름을 우선합니다. 해당 작업 브랜치가 있으면 계속 사용합니다.
- 이번 작업의 파일/hunk만 명시적으로 stage하고, **staged diff 본문·경로를 확인한 후 별도 호출로 커밋**합니다. 다른 작업자의 변경·비밀값·생성물을 포함하지 않습니다. 소유권이 섞여 안전하게 분리할 수 없으면 커밋을 보류하고 필요한 구분을 알립니다.
- 제목은 `type(scope): 한국어 변경 요약`이며 `추가`, `차단`, `검증` 등 명사형으로 끝냅니다. `~한다`형은 쓰지 않습니다. [유형](change-types.md#change-types)은 실제 목적, 선택적인 scope는 실제 모듈·영역입니다. 예: `fix(auth): 다른 발급자의 Access Token 거부`.
- 호환성 파괴는 `type(scope)!: ...`와 본문의 깨지는 계약·전환 방법으로 표시합니다. 비단순 변경에는 문제·이유·실제 검증 근거를 적고, 제목만으로 이유가 명백하면 본문을 생략할 수 있습니다. 실제 관련 이슈만 연결하며 대화·실행 로그를 전재하지 않습니다.
- 실패·필수 집중 검사 미실행 단위는 자동 커밋하지 않습니다. 중간 커밋 뒤 전체 검사 실패는 수정·검증한 새 커밋으로 보완합니다. 조사·리뷰만 요청받으면 임의 변경을 만들지 않고, 명시된 커밋 금지를 지킵니다.
- 자동 이력 작업은 새 커밋 생성입니다. amend·rebase·reset·브랜치 삭제는 옵션 순서·별칭과 무관하게 [승인 절차](approvals/git.md#git)를 따릅니다.
- 커밋 후 해시·목적·실제 검사 결과·남은 전체 검증을 보고합니다. 커밋은 푸시·PR 생성·병합 권한이 아닙니다.
