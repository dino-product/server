# 스케줄 컨텍스트 (`schedule`) — Core Subdomain

- 기준일: 2026-10-01
- 기획 원본: [기획 원본 색인](../planning/README.md#planning)의 [작업]·[스케줄·배정]·[현장 수행]·[현황 파악] 정책서. 표기(`[작업] §5`)·차이 ID·용어 대응은 색인을 따른다
- 다른 컨텍스트와의 관계·로드맵: [바운디드 컨텍스트 지도](bounded-contexts.md#schedule)

이 문서는 `schedule`의 설계·구현 결정과 Notion 기획과의 차이를 소유한다. 제품 규칙(누가·무엇을·언제, 사용자가 체감하는 제한)은 다시 적지 않고 Notion 절 번호로만 참조한다. 현재 구현 범위와 공개 계약은 [도메인 지도](README.md#모듈별-책임과-공개-계약), 작업 지침·오류 순서는 [schedule 지침](../../src/main/java/com/orbit/schedule/AGENTS.md)이 원본이다.

## 개요

| 항목 | 내용 |
| --- | --- |
| 책임 | 작업 등록부터 완료까지 전체 생애주기. 발주–배정–수행의 최소 단위를 다룸 |
| 상태 | 구현 중 — 구현된 범위는 [도메인 지도](README.md#모듈별-책임과-공개-계약), 작업 지침은 [schedule 지침](../../src/main/java/com/orbit/schedule/AGENTS.md) |
| 기획 원본 | [작업] 정책 · [스케줄·배정] 정책 · [현장 수행] 정책 · [현황 파악] 정책 |
| 소유 애그리게잇 | **Work**(Root) — 소속 조직(Organization ID 참조), 작업명, 등록자(Membership ID 참조)·담당기사(Technician ID 참조), 시간, 상태<br>├ AssignmentHistory(내부 엔티티) — 배정 시도마다 일정·배정한 관리자·배정/응답 시각·결과·관리자 조치로 끝난 기록, 최신 이력이 현재 배정<br>├ CompletionReport(내부 엔티티) — 완료보고(사진·메모·실제 결제), Work와 생명주기 완전히 묶임<br>└ WorkSchedule/CustomerInfo/PaymentInfo/Money/Cancellation(VO) — 담당기사·시작시각·예상소요시간 / 고객정보 / 결제정보 / 원 단위 금액 / 취소 시각·처리자·사유 |
| 상태 흐름 | 등록(대기함) → 배정됨 → 작업전 → 작업중 → 완료, 별도 종점 취소. 표시값·전이 조건·권한은 [제품 규칙 참조](#schedule-product), 코드값은 [구현 결정](#schedule-implementation) |
| 읽기 모델 | Timetable/Backlog/ProgressBoard — **애그리게잇 아님.** Work를 기사×시간 축이나 상태별로 투영한 조회 결과일 뿐, 자체 쓰기 불변식이 없음 |
| 관계 | `organization` → 참조(ID) (등록자가 Work의 조직에 속한 활성 Membership인지, 담당기사가 그 조직의 활성 기사 계약인지, 작업 유형이 같은 조직의 WorkType인지 확인, ACL — organization의 소속·기사 계약을 schedule의 요청자(`Actor`)로 번역해 역할별 규칙을 적용하기 때문. 도메인은 ID만 보유하므로 Application이 등록·기본정보 수정·배정·재배정 때 검증. 작업 유형은 요청에 값이 있으면(비우지 않았으면) 매번 확인. 요청자는 organization 공개 계약 `OrganizationMemberLookup`으로 확인하고, 담당기사·작업 유형 검증과 일정 변경 때 현재 담당기사를 다시 확인할지는 그 검증을 연결할 때 정한다) · `notification` ← 이벤트 발행(작업 상태 변경) |

> **명명 정정**: 기획 문서에서는 이 애그리게잇을 "Job"이라 부르지만, 레포는 `*WorkUseCase` 명명을 먼저 써 왔으므로 **애그리게잇명은 "Work"로 통일**한다. 이후 모든 코드·레포 문서에서 Job이라는 이름은 쓰지 않는다.
>
> **모듈명과 애그리게잇명 구분**: BC(모듈) 이름은 `schedule`, 그 안의 유일한 애그리게잇 이름은 `Work`다. 모듈은 작업 등록부터 완료까지 전체 스케줄링 생애주기를 다루는 컨텍스트 단위이고, 애그리게잇은 그 컨텍스트가 소유하는 구체적 도메인 객체다 — 이름이 다른 것은 의도된 설계이며 오기가 아니다.

## 구현 결정

사용자에게 드러나지 않는 규칙 중 여러 유즈케이스에 걸치는 **모듈 공통 규칙**만 둔다. **이 절이 원본**이며, 모듈 공통 규칙을 새로 정하거나 바꿀 때만 고친다. 유즈케이스 하나에만 해당하는 판단(그 기능의 오류 코드 등)은 Javadoc과 PR의 기술적 선택에 둔다. 제품 규칙이 정하지 않은 값을 여기서 새로 정하지 않는다(그런 항목은 [차이·공백](#schedule-gaps)에 적는다).

- **상태 코드값**: `REGISTERED`(등록) · `PENDING_ACCEPTANCE`(배정됨) · `ACCEPTED`(작업전) · `IN_PROGRESS`(작업중) · `COMPLETED`(완료) · `CANCELLED`(취소). 대기함은 상태가 아니라 기사·시간이 없는 `REGISTERED` 작업을 보여주는 조회 조건이다. 거절은 상태가 아니라 배정 이력의 결과로만 남는다. `PENDING_ACCEPTANCE` 중의 재배정·일정 변경처럼 상태가 그대로인 변경은 전이가 아니며, 전이 규칙은 자기 자신으로의 전이를 허용하지 않는다.
- **업무별 전이**: 상태는 업무별 메서드(배정·수락·거절·재배정·일정 변경·배정 해제·시작·완료보고 제출·취소)로만 바꾼다. 허용 경로 없이 상태만 주입하는 방식은 불변식을 깨므로 도메인에 두지 않는다. 관리자 강제 변경을 도입하게 되면 명시적 전이표와 도착 상태의 필수 데이터 검증을 함께 둔다(도입 여부는 S-11).
- **기사 요청의 배정 확인**: 기사의 수락·거절·시작·완료보고는 기사가 본 배정 순번이 여전히 최신일 때만 받는다. 배정 순번은 배정 이력의 1부터 시작하는 위치이며 이력은 추가만 되므로 바뀌지 않는다. 같은 기사가 같은 배정에 같은 요청을 다시 보내면(수락, 같은 사유·메모의 거절, 시작, 같은 내용의 완료보고) 아무것도 바꾸지 않고 성공한다.
- **배정 이력**: 배정 시도마다 담당기사·일정·배정한 관리자(`assignedBy`)·배정 시각(`assignedAt`)·응답 시각(`decidedAt`)·결과를 남긴다. 관리자의 재배정·일정 변경·배정 해제·취소로 배정이 끝나면 종료 기록(시각·처리자·방식)을 남긴다. 응답 전에 끝난 이력은 결과를 응답 전 회수(`WITHDRAWN`)로 확정하고 응답 시각은 회수 시각으로 두며, 이미 수락된 이력은 결과를 그대로 둔 채 종료만 더한다. 거절은 기사의 응답이라 종료 기록이 없고, 수락·거절은 담당 기사 본인만 하므로 처리자를 따로 남기지 않는다. 현재 배정은 최신 이력이며 그보다 앞선 이력은 모두 거절됐거나 끝나 있다. 새 배정 시각은 최신 이력의 마지막 시각(종료·응답·배정 시각 중 가장 늦은 것)보다 앞설 수 없다.
- **완료보고**: 보고 저장과 완료 전환은 함께 성공·실패하고 완료 시각을 남긴다. 사진은 업로드를 먼저 마친 파일의 식별자로 받는다.
- **취소 기록**: 취소 시각·처리자·사유를 작업에 남기고, 배정이 있던 작업은 그 배정도 같은 시각·처리자의 취소로 끝낸다. 작업중 취소는 시작 시각을 그대로 남긴다.
- **기본정보 수정**: 작업명·작업 유형·고객정보(현장 주소 포함)·결제정보를 한꺼번에 교체하며 비운 항목은 지운다. 상태 전이가 아니다(수정 뒤 배정·수락을 어떻게 처리할지는 S-14).
- **저장 상태 복원**: 복원할 때도 상태와 데이터의 정합성(`PENDING_ACCEPTANCE` 이후 일정 존재, 완료 시 완료보고 존재, 배정 이력의 시간 순서, 최신 이력 앞의 배정은 모두 끝났음, 최신 이력의 종료 방식이 작업 상태와 맞음, 재배정·일정 변경 종료 뒤에는 그 조치가 만든 배정이 이어짐, 작업중·완료면 시작 시각이 있고 완료면 완료 시각이 있음(작업중에 취소된 작업만 취소 뒤에도 시작 시각을 가짐), 수락 → 시작 → 완료·취소의 시간 순서, 취소된 작업에만 취소 기록이 있고 배정 중 취소면 그 배정의 취소 종료와 시각·처리자가 같으며 대기함 취소면 배정 이력의 마지막 시각보다 앞서지 않음 등)을 검증한다.
- **일정 충돌 판정**: 같은 기사 계약의 활성 작업(`PENDING_ACCEPTANCE`·`ACCEPTED`·`IN_PROGRESS`)과 반열림 구간 `[시작, 종료)`이 겹치는지 본다. 배정할 수 있는 요청(상태·입력 통과)만 판정하며, 겹치는데 확인 표시가 없는 요청은 반영하지 않고 겹친 작업을 시작시각 순으로 돌려준다(오류가 아님). 확인 뒤 저장하는 규칙은 [스케줄·배정] §8을 따른다. 일정 변경은 자기 자신의 기존 일정을 충돌 검사에서 제외한다.
- **동시성**: 같은 조직·기사의 일정 변경(배정·재배정·일정 변경)은 겹침 판정 전에, 작업 시작은 작업중 판정 전에 기사 단위 PostgreSQL advisory lock으로 한 줄로 세워, 동시에 들어온 요청도 앞선 요청의 저장 결과를 보고 판정한다. 기다림이 대기 한도를 넘기면 "잠시 후 다시 시도"로 거부한다(409). 같은 작업에 대한 경합은 버전 검사로 막는다(HM-234, [schedule 지침](../../src/main/java/com/orbit/schedule/AGENTS.md)).
- **시각**: 작업 일정과 이력 시각은 UTC `Instant`로 다룬다([트랜잭션과 시간](../../.claude/skills/dino-architecture/references/persistence.md#transactions)). 화면에 어느 시간대로 보여 줄지는 서버가 정하지 않는다. 시작시각·예상소요시간과 기록 시각(배정·응답·종료·작업 시작·완료·취소)은 저장소 정밀도인 마이크로초까지만 다루고 그보다 작은 단위는 잘라낸다.
- **금액**: 원화에는 소수 단위가 없으므로 작업 금액과 실제 결제 금액은 원 단위 정수 값객체 `Money`로 다루고 정수 컬럼에 저장한다. 금액의 허용 범위는 S-13을 따른다.
- **결제 방식 대응**: 등록 시 계획 결제 방식과 완료보고의 실제 결제 방식은 코드(`PaymentMethod`)에서 1:1로 대응한다(현장 카드↔신용카드, 현장 현금↔현금, 계좌이체↔계좌이체). 아직 쓰는 곳은 없고, 계획과 실제를 비교할 때 쓴다(청구서 후불의 대응은 S-08 해소 때 정한다). 완료보고 항목이 모두 선택 입력인 것은 [현장 수행] §6을 따르며, 서버는 비어 있는 실제 금액·결제 방식을 계획값으로 채우지 않는다(화면의 미리 채우기는 클라이언트 책임).
- **권한 판정 방식**: 총관리자·직원은 조직 소속(Membership)으로, 기사는 조직과 맺은 기사 계약(Technician)으로 판정하고 서로 다른 ID로 참조한다. 직원 유형(예: 상담·팀장)은 분류용 라벨이며 판정에 쓰지 않는다. 기사에게 보여서는 안 되는 작업은 다른 조직 작업처럼 404로 존재를 숨긴다(어떤 작업이 보이는지는 S-04). 오류 코드와 확인 순서는 [schedule 지침](../../src/main/java/com/orbit/schedule/AGENTS.md#오류-순서)이 원본이다.
