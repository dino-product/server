# 스케줄 컨텍스트 (`schedule`) — Core Subdomain

- 기준일: 2026-10-01
- 기획 원본: [기획 원본 색인](../planning/README.md#planning)의 [작업]·[스케줄·배정]·[현장 수행]·[현황 파악] 정책서. 표기(`[작업] §5`)·차이 ID·용어 대응은 색인을 따른다
- 다른 컨텍스트와의 관계·로드맵: [바운디드 컨텍스트 지도](bounded-contexts.md#schedule)

이 문서는 `schedule`의 설계·구현 결정과 Notion 기획과의 차이를 소유한다. 제품 규칙(누가·무엇을·언제, 사용자가 체감하는 제한)은 다시 적지 않고 Notion 절 번호로만 참조한다. 현재 구현 범위와 공개 계약은 [도메인 지도](README.md#모듈별-책임과-공개-계약), 작업 지침·오류 순서는 [schedule 지침](../../src/main/java/com/orbit/schedule/AGENTS.md)이 원본이다.

## 개요

| 항목 | 내용 |
| --- | --- |
| 책임 | 작업 등록부터 완료까지 전체 생애주기. 발주–배정–수행의 최소 단위를 다룸 |
| 상태 | 구현 중 — 구현된 범위는 [도메인 지도](README.md#모듈별-책임과-공개-계약), 작업 지침은 [schedule 지침](../../src/main/java/com/orbit/schedule/AGENTS.md) |
| 기획 원본 | [작업] 정책 · [스케줄·배정] 정책 · [현장 수행] 정책 · [현황 파악] 정책 |
| 소유 애그리게잇 | **Work**(Root) — 소속 조직(Organization ID 참조), 작업명, 등록자(Membership ID 참조)·담당기사(Technician ID 참조), 시간, 상태<br>├ AssignmentHistory(내부 엔티티) — 배정 시도마다 일정·배정한 관리자·배정/응답 시각·결과·관리자 조치로 끝난 기록, 최신 이력이 현재 배정<br>├ CompletionReport(내부 엔티티) — 완료보고(사진·메모·실제 결제), Work와 생명주기 완전히 묶임<br>├ 현장 사진 — 등록·기본정보 수정 때 붙인 업로드 파일 식별자 목록(최대 6장), Work와 생명주기 완전히 묶임<br>└ WorkSchedule/CustomerInfo/SiteAddress/PaymentInfo/Money/Cancellation(VO) — 담당기사·시작시각·예상소요시간 / 고객정보 / 현장 주소(우편번호·기본·상세) / 결제정보 / 원 단위 금액 / 취소 시각·처리자·사유 |
| 상태 흐름 | 등록(대기함) → 배정됨 → 작업전 → 작업중 → 완료, 별도 종점 취소. 표시값·전이 조건·권한은 [제품 규칙 참조](#schedule-product), 코드값은 [구현 결정](#schedule-implementation) |
| 읽기 모델 | Timetable/Backlog/ProgressBoard — **애그리게잇 아님.** Work를 기사×시간 축이나 상태별로 투영한 조회 결과일 뿐, 자체 쓰기 불변식이 없음 |
| 관계 | `organization` → 참조(ID) (등록자가 Work의 조직에 속한 활성 Membership인지, 담당기사가 그 조직의 활성 기사 계약인지, 작업 유형이 같은 조직의 WorkType인지 확인, ACL — organization의 소속·기사 계약을 schedule의 요청자(`Actor`)로 번역해 역할별 규칙을 적용하기 때문. 도메인은 ID만 보유하므로 Application이 등록·기본정보 수정·배정·재배정 때 검증. 작업 유형은 등록이면 유형을 줬을 때, 기본정보 수정이면 유형이 바뀌고 비우지 않았을 때만 확인. 요청자는 organization 공개 계약 `OrganizationMemberLookup`으로 확인하고, 담당기사는 schedule 출력 포트 `TechnicianContractPort`로 organization 공개 계약 `TechnicianContractLookup`에 묻고, 작업 유형은 `WorkTypePort`로 확인하며 organization 계약(HM-295)이 생기기 전에는 임시 어댑터가 거부한다. 담당기사를 잠근 뒤 확인하는 규칙은 구현 결정의 동시성을 따른다. 일정 변경은 현재 담당기사를 다시 확인하지 않는다(비활성화·역할 변경은 `TechnicianWorkRelease`로 배정을 풀기 때문. 탈퇴는 S-21). 탈퇴 판정·반환은 계정의 기사 계약을 ACL 출력 포트 `AccountTechnicianContractsPort`(계정 → 비활성 포함 기사 계약)로 같은 `TechnicianContractLookup`에서 찾는다. 조회 화면의 표시 정보(기사 계약·소속·유형)도 ACL 출력 포트 `LoadTechnicianProfilesPort`·`LoadStaffProfilesPort`·`LoadWorkTypeLabelsPort`로 찾으며, 계약 전에는 빈 결과를 돌려주는 임시 어댑터를 둔다) · `profile` → 예정: 이름 조회 `ProfileLookup` 사용(HM-305, 표시 정보 포트의 계정 이름 — 실제 어댑터를 붙일 때 `allowedDependencies`에 `profile` 추가), HM-308 병합 뒤: 요구 인터페이스 `WithdrawalBlocker` 구현(탈퇴 차단, [조직·계정] §5.1)과 이벤트 `AccountWithdrawn` 구독(대기함 반환, [조직·계정] §5.1·[스케줄·배정] §9) · `notification` ← 이벤트 발행(작업 상태 변경) |

> **명명 정정**: 기획 문서에서는 이 애그리게잇을 "Job"이라 부르지만, 레포는 `*WorkUseCase` 명명을 먼저 써 왔으므로 **애그리게잇명은 "Work"로 통일**한다. 이후 모든 코드·레포 문서에서 Job이라는 이름은 쓰지 않는다.
>
> **모듈명과 애그리게잇명 구분**: BC(모듈) 이름은 `schedule`, 그 안의 유일한 애그리게잇 이름은 `Work`다. 모듈은 작업 등록부터 완료까지 전체 스케줄링 생애주기를 다루는 컨텍스트 단위이고, 애그리게잇은 그 컨텍스트가 소유하는 구체적 도메인 객체다 — 이름이 다른 것은 의도된 설계이며 오기가 아니다.

## 구현 결정

사용자에게 드러나지 않는 규칙 중 여러 유즈케이스에 걸치는 **모듈 공통 규칙**만 둔다. **이 절이 원본**이며, 모듈 공통 규칙을 새로 정하거나 바꿀 때만 고친다. 유즈케이스 하나에만 해당하는 판단(그 기능의 오류 코드 등)은 Javadoc과 PR의 기술적 선택에 둔다. 제품 규칙이 정하지 않은 값을 여기서 새로 정하지 않는다(그런 항목은 [차이·공백](#schedule-gaps)에 적는다).

- **상태 코드값**: `REGISTERED`(등록) · `PENDING_ACCEPT`(배정됨) · `ACCEPTED`(작업전) · `IN_PROGRESS`(작업중) · `COMPLETED`(완료) · `CANCELED`(취소)([작업] §9). 대기함은 상태가 아니라 배정되지 않은(실제 일정이 없는) `REGISTERED` 작업을 보여주는 조회 조건이며, 등록 때 미리 입력한 기사·시간은 있을 수 있다. 거절은 상태가 아니라 배정 이력의 결과로만 남는다. `PENDING_ACCEPT` 중의 재배정·일정 변경처럼 상태가 그대로인 변경은 전이가 아니며, 전이 규칙은 자기 자신으로의 전이를 허용하지 않는다.
- **업무별 전이**: 상태는 업무별 메서드(배정·수락·거절·재배정·일정 변경·배정 해제·시작·완료보고 제출·취소)로만 바꾼다. 허용 경로 없이 상태만 주입하는 방식은 불변식을 깨므로 도메인에 두지 않는다. 역방향 강제 전이는 두지 않는다([작업] §7·§13).
- **기사 요청의 배정 확인**: 기사의 수락·거절·시작·완료보고는 기사가 본 배정 순번이 여전히 최신일 때만 받는다. 배정 순번은 배정 이력의 1부터 시작하는 위치이며 이력은 추가만 되므로 바뀌지 않는다. 같은 기사가 같은 배정에 같은 요청을 다시 보내면(수락, 시작, 같은 내용의 완료보고) 아무것도 바꾸지 않고 성공한다. 거절한 작업은 그 기사가 볼 수 없으므로 거절을 다시 보내면 404다.
- **배정 이력**: 배정 시도마다 담당기사·일정·배정한 관리자(`assignedBy`)·배정 시각(`assignedAt`)·응답 시각(`decidedAt`)·결과를 남긴다. 관리자의 재배정·일정 변경·배정 해제·취소로 배정이 끝나면 종료 기록(시각·처리자·방식)을 남긴다. 응답 전에 끝난 이력은 결과를 응답 전 회수(`WITHDRAWN`)로 확정하고 응답 시각은 회수 시각으로 두며, 이미 수락된 이력은 결과를 그대로 둔 채 종료만 더한다. 거절은 기사의 응답이라 종료 기록이 없고, 수락·거절은 담당 기사 본인만 하므로 처리자를 따로 남기지 않는다. 담당 기사의 탈퇴로 대기함에 돌린 배정은 처리한 관리자가 없어 종료 방식 `ACCOUNT_WITHDRAWN`에 처리자를 비우며, 그 밖의 종료는 처리자가 반드시 있다. 현재 배정은 최신 이력이며 그보다 앞선 이력은 모두 거절됐거나 끝나 있다. 새 배정 시각은 최신 이력의 마지막 시각(종료·응답·배정 시각 중 가장 늦은 것)보다 앞설 수 없다.
- **완료보고**: 보고 저장과 완료 전환은 함께 성공·실패하고 완료 시각을 남긴다. 사진은 업로드를 먼저 마친 파일의 식별자로 받는다.
- **취소 기록**: 취소 시각·처리자·사유를 작업에 남기고, 배정이 있던 작업은 그 배정도 같은 시각·처리자의 취소로 끝낸다. 작업중 취소는 시작 시각을 그대로 남긴다.
- **보일 일정**: 작업 목록·출력의 담당기사·예정시간 칸과 진행 보드의 카드는 `Work.shownSchedule()`이다(진행 보드는 시간이 구간에 든 대기함 작업을 등록 열에 담는다, [현황 파악] §4 MON-003). 지금 일정이 있으면 그 일정, 대기함 작업이면 미리 입력한 일정이나 배정됐다 돌아온 작업의 마지막 배정 일정이다(반환한 기사가 비활성·탈퇴했어도 그대로 보인다. 미리 입력한 담당기사만 §9대로 비운다). 같은 일정 컬럼에 저장해 목록의 담당기사·기간 조건과 예정시간 정렬, 지연 조건이 같은 값을 쓴다([작업] §6 JOB-010).
- **지연**: 예정 종료 시각이 지났는데 끝나지 않은 작업(배정됨·작업전·작업중, 보일 일정이 있는 대기함 작업)과 예정 종료 시각이나 그 뒤에 완료한 작업이다(`Work.isDelayedAt`, [현황 파악] §5). 취소 작업은 지연이 아니다.
- **미리 입력한 일정**: 등록 때 담당기사·시작시각·예상소요시간을 일부만 받으면 `PlannedSchedule`로 대기함 작업에 남긴다. 대기함 작업만 가지며 배정하면 실제 일정으로 대체되고, 취소하면 지운다. 거절·배정 해제로 대기함에 돌아온 작업은 남기지 않는다. 저장은 실제 일정과 같은 `technician_id`·`scheduled_start_at`·`expected_duration` 컬럼을 쓰고 상태가 등록이며 배정 이력이 없으면 미리 입력한 일정으로 읽는다(기사의 활성 작업 조회는 상태로 걸러 영향이 없다). 미리 입력한 담당기사도 그 조직의 활성 기사 계약이어야 하며, 그 기사를 잠근 뒤 확인한다. 기사의 역할 변경·비활성화·탈퇴로 배정됨·작업전 작업을 대기함으로 돌릴 때 같은 잠금 안에서 그 기사를 가리키는 미리 입력한 담당기사를 비우고 시작시각·예상소요시간은 남긴다([스케줄·배정] §9).
- **등록 시각**: 작업은 등록 시각을 가지며 `registered_at`에 저장한다(감사 컬럼 `created_at`과 별개). 배정·취소 같은 뒤따르는 기록은 등록 시각보다 앞서지 않는다. 등록 시각은 대기함 방치 판정([스케줄·배정] §5, SCH-009)의 기준이며, 거절·해제·반환으로 돌아온 작업도 다시 세지 않는다.
- **최근 수정 시각**: 작업 목록의 최근 수정일과 그 정렬은 감사 컬럼 `updated_at`을 조회 출력 포트 결과(`WorkSearchResult.SearchedWork`)로만 내보낸다. Domain에는 올리지 않고 업무 판정에도 쓰지 않는다. 저장 시점(flush) 값이라 업무 기록 시각과 조금 어긋날 수 있고, JPA로 일괄 갱신하면 함께 바뀌며 SQL 일괄 갱신은 바꾸지 않는다. 루트 행이 바뀔 때만 갱신되는 전제는 `WorkMapper`가 적는다.
- **기본정보 수정**: 작업명·작업 유형·고객정보(현장 주소 포함)·결제정보·현장 사진을 한꺼번에 교체하며 비운 항목은 지운다. 작업 유형은 바뀔 때만 그 조직에서 고를 수 있는지 확인한다(지금 유형을 그대로 보낸 수정은 확인하지 않음). 상태 전이가 아니다(수정 뒤 배정·수락을 어떻게 처리할지는 S-14).
- **저장 상태 복원**: 복원할 때도 상태와 데이터의 정합성(`PENDING_ACCEPT` 이후 일정 존재, 완료 시 완료보고 존재, 배정 이력의 시간 순서, 최신 이력 앞의 배정은 모두 끝났음, 최신 이력의 종료 방식이 작업 상태와 맞음, 재배정·일정 변경 종료 뒤에는 그 조치가 만든 배정이 이어짐, 작업중·완료면 시작 시각이 있고 완료면 완료 시각이 있음(작업중에 취소된 작업만 취소 뒤에도 시작 시각을 가짐), 수락 → 시작 → 완료·취소의 시간 순서, 취소된 작업에만 취소 기록이 있고 배정 중 취소면 그 배정의 취소 종료와 시각·처리자가 같으며 대기함 취소면 배정 이력의 마지막 시각보다 앞서지 않음 등)을 검증한다.
- **일정 충돌 판정**: 같은 기사 계약의 활성 작업(`PENDING_ACCEPT`·`ACCEPTED`·`IN_PROGRESS`)과 반열림 구간 `[시작, 종료)`이 겹치는지 본다. 배정할 수 있는 요청(상태·입력 통과)만 판정하며, 겹치는데 확인 표시가 없는 요청은 반영하지 않고 겹친 작업을 시작시각 순으로 돌려준다(오류가 아님). 확인 뒤 저장하는 규칙은 [스케줄·배정] §8을 따른다. 일정 변경은 자기 자신의 기존 일정을 충돌 검사에서 제외한다.
- **동시성**: 같은 조직·기사의 일정 변경(배정·재배정·일정 변경)은 겹침 판정 전에 기사 단위 PostgreSQL advisory lock으로 한 줄로 세워, 동시에 들어온 요청도 앞선 요청의 저장 결과를 보고 판정한다. 기다림이 대기 한도를 넘기면 "잠시 후 다시 시도"로 거부한다(409). 기사 요청(수락·거절·시작)은 작업 식별자 형식을 확인한 뒤 작업을 읽기 전에 기사를 잠가, 같은 기사를 잠그는 대기함 반환·일정 변경·같은 작업의 중복 요청과 한 줄로 선다(시작은 같은 기사의 다른 작업이 작업중이어도 막지 않으므로 다른 작업은 읽지 않는다, [현장 수행] §5 FLD-007). 뒤에 온 쪽이 앞선 커밋을 보고 판정하므로 반환과의 경합에서 버전 충돌이 나지 않는다: 반환이 먼저면 기사 요청이 404이고, 시작이 먼저면 비활성화·탈퇴 반환은 그 작업을 두고 역할 변경은 막히며, 수락·거절이 먼저면 반환이 그 결과를 보고 처리한다. 같은 요청의 중복 전송은 성공(거절은 404)이고, 일정 변경과는 늦은 쪽이 409다(기사 요청은 배정이 바뀜, 일정 변경은 버전 충돌). 완료보고는 반환이 바꾸는 작업(배정됨·작업전)을 건드리지 않아 잠그지 않는다. 배정·재배정은 잠근 뒤 담당기사의 활성 기사 계약을 확인하므로, 기사 비활성화·역할 변경의 대기함 반환(`TechnicianWorkRelease` 구현)도 같은 기사 잠금을 거쳐 반환과 동시에 실행된 배정이 비활성 기사에게 남지 않게 한다. 일부만 입력한 등록도 미리 입력한 담당기사를 잠근 뒤 확인해, 반환과 동시에 등록한 작업이 비활성·탈퇴한 기사를 가리키지 않게 한다([스케줄·배정] §9). 반환은 organization 트랜잭션에 참여해 격리 수준을 지정할 수 없으므로 PostgreSQL 기본값(READ COMMITTED)에 기대고, 바깥 트랜잭션이 그보다 높은 격리 수준을 지정했으면 잠그기 전에 거부한다. 탈퇴 뒤처리는 한 계정의 여러 조직 기사 계약을 한 트랜잭션에서 잠그므로 조직·기사 계약 ID 오름차순으로 잠근다(다른 유즈케이스는 한 기사만 잠그고, 한 계정은 한 조직과 기사 계약을 하나만 맺는다). 탈퇴 차단 판정은 잠그지 않으며, 판정 뒤 탈퇴 커밋 전에 생긴 배정은 탈퇴 뒤처리가 함께 돌린다. 남는 위험(해소 방향 미정, HM-320): (a) 판정 뒤 탈퇴 반환이 그 기사를 잠그기 전에 작업 시작이 커밋되면 탈퇴한 계정에 작업중 작업이 남는다(반환은 작업중 작업을 두므로). 비활성화와 탈퇴 뒤처리는 탈퇴 커밋 뒤에 도는 리스너라, 판정에서 기사를 잠가도 비활성화 전에 요청자 확인을 통과한 시작은 막지 못한다. (b) 탈퇴 뒤처리와 organization의 계약 비활성화는 같은 이벤트의 별도 리스너라 순서가 없다. schedule 반환이 비활성화보다 먼저 끝나면 그 사이 생긴 배정과 일부만 입력한 등록의 미리 입력한 담당기사가 탈퇴한 기사를 가리킨 채 남고, 반환은 이미 성공했으므로 재전송으로도 처리되지 않는다. 계정의 기사 계약 조회는 비활성 계약까지 돌려줄 뿐 비활성화와의 순서를 보장하지 않으며, 해소 방향(비활성화 뒤 반환 등 순서 보장)은 정하지 않았다. 같은 작업에 대한 경합은 버전 검사로 막는다. 배정 변경·배정 해제는 요청자가 화면에서 본 작업 버전을 받아 지금 버전과 비교하고, 저장 자리에서 다른 트랜잭션이 먼저 바꾼 것이 드러나도 같은 409로 거부한다([스케줄·배정] §7). 기본정보 수정은 [작업] §5대로 나중 저장이 이긴다(동시에 열린 트랜잭션끼리 겹치면 뒤 저장이 500). 나머지 유즈케이스의 충돌 변환은 HM-236([schedule 지침](../../src/main/java/com/orbit/schedule/AGENTS.md))이 남은 범위다.
- **작업 목록 기본 상태**: 작업 목록 검색·건수·작업내역 출력은 상태 조건을 비우면 취소를 뺀 모든 상태를 담고, 취소 작업은 상태 조건에 취소를 넣어야 담는다([작업] §6 JOB-001). 기본값은 `WorkSearchConditions` 한 곳에서 정한다.
- **시각**: 작업 일정과 이력 시각은 UTC `Instant`로 다룬다([트랜잭션과 시간](../../.claude/skills/dino-architecture/references/persistence.md#transactions)). 화면에 어느 시간대로 보여 줄지는 서버가 정하지 않는다. 시작시각·예상소요시간과 기록 시각(배정·응답·종료·작업 시작·완료·취소)은 저장소 정밀도인 마이크로초까지만 다루고 그보다 작은 단위는 잘라낸다.
- **금액**: 원화에는 소수 단위가 없으므로 작업 금액과 실제 결제 금액은 원 단위 정수 값객체 `Money`로 다루고 정수 컬럼에 저장한다. 금액의 허용 범위는 [작업] 기능명세 §5를 따른다(0원 이상).
- **결제 방식 대응**: 등록 시 계획 결제 방식과 완료보고의 실제 결제 방식은 코드(`PaymentMethod`)에서 1:1로 대응한다(현장 카드↔신용카드, 현장 현금↔현금, 계좌이체↔계좌이체, 청구서 발행(후불)↔청구서 발행(후불)). 아직 쓰는 곳은 없고, 계획과 실제를 비교할 때 쓴다. 완료보고 항목이 모두 선택 입력인 것은 [현장 수행] §6을 따르며, 서버는 비어 있는 실제 금액·결제 방식을 계획값으로 채우지 않는다(화면의 미리 채우기는 클라이언트 책임).
- **권한 판정 방식**: 총관리자·직원은 조직 소속(Membership)으로, 기사는 조직과 맺은 기사 계약(Technician)으로 판정하고 서로 다른 ID로 참조한다. 직원 유형(예: 상담·팀장)은 분류용 라벨이며 판정에 쓰지 않는다. 기사에게는 작업에 남은 일정의 기사가 자기인 작업(지금 배정된 작업과 취소 당시 담당이던 취소 작업)만 보이고, 나머지(거절함·다른 기사로 재배정됨·배정 해제·반환됨·배정받은 적 없음)는 다른 조직 작업처럼 404로 존재를 숨긴다([스케줄·배정] §10, [현장 수행] §4·§11, `AssignedTechnicians`). 기사 상세의 배정 이력은 지금 배정 하나만 담는다. 오류 코드와 확인 순서는 [schedule 지침](../../src/main/java/com/orbit/schedule/AGENTS.md#오류-순서)이 원본이다.
