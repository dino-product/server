# 조직 도메인

`com.orbit.organization.domain`은 프레임워크와 다른 모듈에 의존하지 않는다. 루트 공개 계약은 없고 모듈의 허용 의존성은 없다. 전체 모듈 상태는 [도메인 지도](README.md#모듈별-책임과-공개-계약)를 따른다.

## 용어

인증 경계에서 전달하는 식별자는 `accountId`, 조직이 보유하는 외부 계정 참조는 `authAccountId`다. `AuthAccountId(Long)`는 조직 자체 값객체이며 양수만 허용한다. 직원 소속은 `Membership`, 회사별 기사 계약은 `Technician`, 참여 요청은 `ParticipantRequest`(`participant_request`)다. DB 이름은 후속 영속성 작업의 매핑 기준이며 이 모듈에는 JPA 매핑이 없다.

## 회사·총관리자

`Organization`은 조직명·선택 업종·회사 코드와 필수 `ownerMembershipId`를 보유한다. 조직명은 앞뒤 공백 제거 후 유니코드 코드포인트 2~30자다. 업종은 냉난방 설비 / 전기·전자 / 배관·설비 / 가전 A/S / 종합 시설관리 / 기타 중 선택하며 null로 미지정·해제할 수 있다.

영속성 어댑터는 `Organization.reconstitute(id, name, industry, code, ownerMembershipId)`로 저장값을 복원한다. 필수 ID·이름·코드·총관리자 소속 ID는 null일 수 없고 업종은 선택이다. 복원 시 총관리자 소속 객체나 현재 활성 상태를 요구하지 않으며, 생성·위임 정책을 다시 실행하지 않는다.

총관리자는 같은 회사의 활성 `Membership` 한 명이며 `ADMIN`과 같은 의미다. 직원에 별도 `role`을 저장하지 않는다. 생성·위임에서 대상 소속의 회사와 활성 상태를 검증하고, 관리 권한은 `isManagedBy`로 판정한다. `deactivateMembership`는 현 총관리자의 비활성화를 거부한다. 위임한 뒤 기존 총관리자를 비활성화할 수 있다. Application은 현재 행위자의 소속을 조회해 관리 권한을 확인하며 위임·비활성화의 동시성을 제어해야 한다.

`CompanyCode`는 정확히 8자의 대문자 Crockford Base32(`0-9A-HJKMNP-TV-Z`, I·L·O·U 제외)만 허용하며 입력값을 변환하지 않는다. 회사 코드는 순수 무작위로 발급하고 중복이면 재발급하며 DB unique 제약으로 충돌을 최종 방어한다. 발급·중복 확인과 코드 변경·폐기 정책은 후속 계층에서 구현한다. 링크·QR 생성은 이번 범위에 포함하지 않는다. 코드 변경은 기존 관계·접수된 참여 요청을 변경하지 않는다.

## 참여 요청

`ParticipantRequest`는 양수 요청 ID·조직 ID·외부 계정 ID, 희망 유형(`STAFF`/`TECHNICIAN`), 경로(`CODE`/`LINK`/`QR`), 요청 시각으로 생성하며 처음 상태는 `PENDING`이다. 시각은 호출자가 UTC `Instant`로 전달한다.

- 승인: `APPROVED`로 바꾸고 필수 확정 유형·처리 시각을 기록한다. 희망 유형은 보존하며 다른 유형으로 확정할 수 있다.
- 거절: `REJECTED`로 바꾸고 선택 사유·처리 시각을 기록한다. null·공백 사유는 미입력으로 취급한다.
- 취소: `CANCELLED`로 바꾸고 처리 시각을 기록한다.
- 세 처리는 `PENDING`에서만 허용한다. 처리 시각은 요청 시각보다 앞설 수 없다. 거부된 변경은 기존 상태를 보존한다.
- 불변식 위반은 `OrganizationRuleViolation`으로 전달하며 HTTP·공통 오류 타입에 의존하지 않는다.

## 직원·기사 유형

`StaffType`과 `TechnicianType`은 각각 독립 애그리게잇·ID를 사용한다. 조직 ID는 생성 후 바뀌지 않는다. 이름은 `PersonnelTypeName`으로 앞뒤 공백 제거 후 유니코드 코드포인트 2~10자를 허용한다. `TypeColor`는 임시 숫자 1~8이며 실제 색상 매핑은 TODO다. 두 값객체만 공유하고 유형 모델은 합치지 않는다.

생성 시 활성 상태이며 이름·색상 변경과 활성화·비활성화를 지원한다. 최소 활성 유형 개수 규칙은 없다. 유형 비활성화가 소속·계약 자체를 비활성화하지 않는다.

## 직원 소속·기사 계약

`Membership`와 `Technician`은 별도 애그리게잇이며 ID·조직 ID·외부 계정 ID는 변경할 수 없다. `role` 필드나 직원↔기사 전환 메서드는 없다. 생성 시 활성 상태이며 유형은 선택이다. 지정할 때는 같은 회사의 활성 유형만 허용하고 null로 해제할 수 있다. 유형이 나중에 비활성화되어도 기존 지정과 관계 활성 상태는 유지한다.

영속성 어댑터는 `Membership.reconstitute(id, organizationId, authAccountId, typeId, joinedAt, active)`로 저장된 유형 ID와 활성 상태를 그대로 복원한다. ID·조직 ID·계정 ID·참여 시각은 필수이고 유형 ID는 선택이다. 복원 시 유형 객체를 요구하거나 생성·유형 변경 정책을 다시 실행하지 않는다.

직원 `joinedAt`, 기사 `contractedAt`은 호출자가 넘기는 생성 시각이며 재활성화로 바뀌지 않는다. 별도 기사 참여일과 마지막 접속 시각은 현재 두지 않는다. 직원 비활성화는 총관리자 보존을 검사할 조직 도메인을 통해서만 호출하도록 패키지 내부로 제한한다. 기사 계약 비활성화는 다른 관계로 전환하거나 삭제하지 않는다.

## 참여 중복 정책

`ParticipationPolicy.requireCanCreateRelationship`은 동일 회사·계정의 기존 `Membership` 또는 `Technician`이 하나라도 있으면 새 관계 생성을 거부한다. 비활성 관계도 포함하며 직원↔기사 전환은 없다. 같은 계정의 다른 회사 관계와 같은 회사의 다른 계정 관계는 허용한다. 비활성 관계를 재활성화할 때는 기존 애그리게잇을 사용한다.

`requireCanRequest`는 기존 관계에 더해 동일 회사·계정의 `PENDING` 요청도 차단한다. 종료된 요청 자체는 새 요청을 차단하지 않지만 승인으로 생성된 관계가 있으면 관계 검사에서 차단한다. 승인 시 관계 생성 검사에는 처리 중인 요청 자체를 중복 요청으로 적용하지 않는다.

두 정책은 조회·잠금을 하지 않는다. 호출자는 **활성 상태로 필터링하지 않은 최신 관계와 대기 요청**을 전달하고 생성 전에 정책을 반드시 호출해야 한다. 빈 조회 결과와 조회 누락(null)은 구분한다. 개별 모델 생성 메서드만 호출해서는 저장소 전체의 중복을 보장할 수 없으며, 교차 테이블 중복과 동시 승인의 직렬화는 후속 영속성 설계에서 보장한다.

## 후속 계층 책임

현재 Application·Adapter는 구현되지 않았다. 참여 요청 모델 자체는 계정·회사 존재, 현재 회사 코드, 행위자 권한, 기존 관계·대기 요청 중복을 조회하지 않는다. 후속 Application은 승인 권한과 중복을 확인하고 승인·직원 소속 또는 기사 계약 생성을 한 트랜잭션에서 처리해야 한다. 저장소는 동시 요청의 중복·상태 충돌도 막아야 한다. 취소는 요청자 본인만 할 수 있으며 이 검증도 인증 경계와 연결하는 Application의 책임이다.
