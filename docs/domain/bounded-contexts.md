# 바운디드 컨텍스트 지도 (P1~P4)

- 상태: 설계 초안 — P1은 모듈 골격 생성, `schedule`의 도메인·일부 Application·Adapter 구현, `auth` 카카오 로그인 구현, P2~P4는 코드 없음
- 기준일: 2026-10-04
- 기획 원본: [기획 원본 색인](../planning/README.md#planning)의 Notion 정책서 (기준 버전은 색인이 소유, 결정 배경은 [ADR-003](../adr/003-planning-source-of-truth.md))

이 문서는 DDD 관점에서 오빗의 바운디드 컨텍스트(BC)를 서브도메인 분류·소유 애그리게잇·컨텍스트 간 관계까지 제안한다. 현재 등록된 모듈 목록·책임 요약·공개 계약·허용 의존성의 원본은 [도메인 지도](README.md#모듈별-책임과-공개-계약)다. 적용된 범위는 `organization`·`schedule`·`notification` 모듈 골격 추가와 `schedule`의 도메인·일부 Application·Adapter와 `auth`의 카카오 로그인·계정·토큰(구현 범위는 도메인 지도 참조)이며, 그 밖의 애그리게잇·관계와 P2~P4는 설계 초안이다. 골격 모듈의 허용 의존성은 현재 없다.

제품 규칙(누가·무엇을·언제, 사용자가 체감하는 제한)은 이 문서에 다시 적지 않는다. 구현이 시작된 BC는 모듈별 문서(현재 [schedule](schedule.md#schedule)·[auth](auth.md))로 분리하고, 이 문서에는 관계·로드맵만 남긴다. 각 BC는 **기획 원본**(기준 정책서) · **제품 규칙 참조**(Notion 절 번호) · **구현 결정**(BC 문서가 원본) · **차이·공백**(Notion과 구현의 차이, 제품 결정 필요 항목)으로 나눠 적는다. 차이·공백 항목은 [대역별 구현 규칙](../planning/README.md#gap-actions)대로 다루며, 운영 절차는 [동기화 규칙](../planning/README.md#sync)을 따른다.

<a id="organization-design"></a>
#### 2.2 설계 결정 (미구현)

모듈이 골격뿐이라 아래는 구현할 때 따를 레포 쪽 설계다. 구현하면서 이 절을 구현 결정으로 옮긴다.

- **참여 요청을 별도 모듈로 분리하지 않는다**: 회사 코드와 참여 요청은 소속 생성 규칙에 포함되고, 승인과 소속 생성이 하나의 유즈케이스에서 함께 성공·실패해야 하므로 `organization` 안의 애그리게잇으로 둔다. 요청 생명주기가 복잡해지거나 별도 팀 경계가 필요해지면 그때 모듈 분리를 검토한다(BC-002).
- **계정과 소속 분리**: 계정은 조직을 모르고, 조직별 직원 소속·기사 계약이 역할·상태를 가진다. 요청에는 희망 유형, 승인 결과에는 확정 유형에 따라 직원 소속 또는 기사 계약을 만든다. 같은 조직 안에서만 중복 소속·대기 요청을 차단하는 규칙은 `organization`이 소유한다.
- **직원 소속과 기사 계약 분리**: 직원 소속(Membership)과 기사 계약(Technician)은 별도 애그리게잇·테이블로 두고, 직원 유형과 기사 유형도 따로 저장한다. 유형 저장소가 달라 직원에게 기사 유형을, 기사에게 직원 유형을 지정할 수 없다.
- **승인·소속 생성의 원자성**: 참여 요청 승인과 소속 생성, 총관리자 지정·해제의 대상 검증과 권한 변경, 역할 변경의 기존 행 종료와 대상 행 생성·재활성화는 각각 하나의 트랜잭션에서 함께 성공·실패한다.
- **schedule에 공개할 개념**: 관리자(직원 소속)와 기사를 서로 다른 ID로 제공한다. schedule은 기사를 조직과 맺은 기사 계약(Technician)으로 참조한다([schedule 구현 결정](schedule.md#schedule-implementation)).
- **총관리자 표현**: 총관리자는 직원 소속의 총관리자 표시로 나타내고 여러 명을 둘 수 있다([조직·계정] §4, ORG-010). 조직은 총관리자를 단일 참조로 가리키지 않으므로 조직과 최초 소속 사이의 순환 참조가 없다. 같은 발주사의 활성 직원 소속만 지정할 수 있고, 마지막 1명은 해제·비활성화할 수 없다. 별도의 중간 관리자 역할은 두지 않는다.
- **역할 변경 행 규칙**: 회원·발주사마다 직원 소속 1행, 기사 계약 1행까지 두고 활성은 둘 중 하나만 허용한다(두 저장소에 걸친 규칙이라 Application이 검증). 역할을 바꾸면 기존 행은 "역할 변경으로 종료" 상태가 되어 관리자 비활성화와 구분되고 참여 인원·소속 목록에서 빠진다. 대상 행은 없으면 만들고 있으면 재활성화하므로 기사 계약 ID가 유지되어 schedule의 배정·작업 이력이 이어진다. 총관리자 소속은 역할 변경 대상이 아니다([조직·계정] §4.1).
- **유형 소프트 삭제**: 직원·기사·작업 유형은 삭제 여부·삭제 시각으로 소프트 삭제하고 복구·비활성화는 없다([조직·계정] §7). 이미 삭제된 유형의 재삭제는 성공으로 처리하고, 삭제된 유형의 지정은 거부한다. 이름 중복은 같은 발주사·같은 종류의 삭제되지 않은 유형끼리만 검사한다. 직원·기사 유형 삭제 시 보존 규칙은 O-33.

| **리포트·통계** | Generic | 전 컨텍스트 이벤트 기반 순수 읽기 집계 | 전 컨텍스트 ← 이벤트 구독 (쓰기 없음) |
| **재고·문서함** | Generic | 자재·문서 관리 | `schedule` → 참조(ID) (첨부파일 id만) — 통합 자체를 최소화(Separate Ways) |

## P4 — 장기 지향점 (미착수)

| 컨텍스트 | 서브도메인 | 책임 | 관계 |
| --- | --- | --- | --- |
| **고객 셀프예약** | Core-adjacent | 최종고객이 직접 빈 슬롯을 선택해 예약 | `schedule`의 Timetable 읽기모델 → 참조 (Open Host Service, 가용 슬롯 조회) · `schedule` ← 참조(예약=Work 초안 생성, Customer-Supplier) |

P2~P4의 포함 여부·시점은 제품 결정이며 각 정책서의 MVP 제외 절(예: [작업] §13, [현장 수행] §14)이 원본이다. 위 표는 도입될 때의 모듈 경계 제안만 담는다.

## 미해결 설계 이슈

모듈 경계·모델링에 관한 레포 쪽 결정만 둔다. 제품 결정이 필요한 항목은 각 BC의 차이·공백에 둔다.

| # | 이슈 | 비고 |
| --- | --- | --- |
| BC-001 | 개인 계정·프로필 관리(마이페이지, 탈퇴)를 어느 컨텍스트가 가질지 | `auth`가 가질지, 별도 "계정" 성격 컨텍스트를 새로 둘지 미정. "계정"이라는 이름을 `organization`에서 뺀 것과 직접 연결된 이슈 |
| BC-002 | 참여 요청(MembershipRequest)을 `organization`에서 분리할 시점 | 현재는 승인·소속 생성의 원자성 때문에 `organization`에 둠 — 요청 생명주기가 복잡해지면 분리 검토 |

정산 포함 여부(구 BC-004)는 [작업] §13에서 MVP 제외로 정해졌고 탈퇴 차단 조건([조직·계정] §5.1)에도 정산이 없어 닫았다. 조직 간 일정 충돌(구 BC-005)은 제품 결정이라 [schedule 차이·공백](schedule.md#schedule-gaps)의 S-31로 옮겼다.
