# 바운디드 컨텍스트 지도 (P1~P4)

- 상태: 설계 초안 — P1은 모듈 골격 생성, `schedule`의 도메인·일부 Application·Adapter 구현, `auth` 카카오·Apple 로그인·계정 폐쇄 구현, `organization` 발주사 생성 구현, `profile` 가입 프로필·약관 동의·탈퇴 구현, P2~P4는 코드 없음
- 기준일: 2026-10-16
- 기획 원본: [기획 원본 색인](../planning/README.md#planning)의 Notion 정책서 (기준 버전은 색인이 소유, 결정 배경은 [ADR-003](../adr/003-planning-source-of-truth.md))

이 문서는 DDD 관점에서 오빗의 바운디드 컨텍스트(BC)를 서브도메인 분류·소유 애그리게잇·컨텍스트 간 관계까지 제안한다. 현재 등록된 모듈 목록·책임 요약·공개 계약·허용 의존성의 원본은 [도메인 지도](README.md#모듈별-책임과-공개-계약)다. 적용된 범위는 `organization`·`schedule`·`notification` 모듈 추가와 `schedule`의 도메인·일부 Application·Adapter, `auth`의 카카오·Apple 로그인·계정·토큰·계정 폐쇄, `organization`의 발주사 생성, `profile`의 가입 프로필·약관 동의·가입 공통 검사·탈퇴, `notification`의 작업 이벤트 알림(구현 범위는 도메인 지도 참조)이며, 그 밖의 애그리게잇·관계와 P2~P4는 설계 초안이다.

제품 규칙(누가·무엇을·언제, 사용자가 체감하는 제한)은 이 문서에 다시 적지 않는다. 구현이 시작된 BC는 모듈별 문서(현재 [schedule](schedule.md#schedule)·[auth](auth.md)·[profile](profile.md#profile))로 분리하고, 이 문서에는 관계·로드맵만 남긴다. 각 BC는 **기획 원본**(기준 정책서) · **제품 규칙 참조**(Notion 절 번호) · **구현 결정**(BC 문서가 원본) · **차이·공백**(Notion과 구현의 차이, 제품 결정 필요 항목)으로 나눠 적는다. 차이·공백 항목은 [대역별 구현 규칙](../planning/README.md#gap-actions)대로 다루며, 운영 절차는 [동기화 규칙](../planning/README.md#sync)을 따른다.

#### 2.2 설계 결정 (부분 구현)

발주사 생성, 발주사 정보 조회·수정, 회사 코드 조회·변경, 총관리자 지정·해제, 회사 확인·참여 요청 생성·취소·내 신청 현황·승인 대기 목록·승인·거절, schedule용 활성 구성원 조회(소속·기사 계약 활성·비활성 상태, 계정·발주사당 소속·계약 각 1행 제약)와 기사 계약 조회(계정의 계약 목록·활성 확인), 내 소속 목록 조회(아래 역할 변경 행 규칙의 발주사당 한 줄), 직원·기사·작업 유형 관리, 참여 인원 목록(같은 행 규칙의 계정당 한 줄)·세부 유형 지정·비활성화·재활성화, schedule용 작업 유형·구성원 표시 정보 조회만 구현됐다. 아래는 구현할 때 따를 레포 쪽 설계이며, 구현하면서 이 절을 구현 결정으로 옮긴다. 구현된 부분(총관리자 표현, 회사 코드 발급·폐기, 참여 요청 잠금)의 작업 규칙은 [organization 지침](../../src/main/java/com/orbit/organization/AGENTS.md)에 있다.

- **참여 요청을 별도 모듈로 분리하지 않는다**: 회사 코드와 참여 요청은 소속 생성 규칙에 포함되고, 승인과 소속 생성이 하나의 유즈케이스에서 함께 성공·실패해야 하므로 `organization` 안의 애그리게잇으로 둔다. 요청 생명주기가 복잡해지거나 별도 팀 경계가 필요해지면 그때 모듈 분리를 검토한다(BC-002).
- **계정과 소속 분리**: 계정은 조직을 모르고, 조직별 직원 소속·기사 계약이 역할·상태를 가진다. 요청에는 희망 유형, 승인 결과에는 확정 유형에 따라 직원 소속 또는 기사 계약을 만든다. 같은 조직 안에서만 중복 소속·대기 요청을 차단하는 규칙은 `organization`이 소유한다.
- **직원 소속과 기사 계약 분리**: 직원 소속(Membership)과 기사 계약(Technician)은 별도 애그리게잇·테이블로 두고, 직원 유형과 기사 유형도 따로 저장한다. 유형 저장소가 달라 직원에게 기사 유형을, 기사에게 직원 유형을 지정할 수 없다.
- **승인·소속 생성의 원자성**: 참여 요청 승인과 소속 생성, 총관리자 지정·해제의 대상 검증과 권한 변경, 역할 변경의 기존 행 종료와 대상 행 생성·재활성화는 각각 하나의 트랜잭션에서 함께 성공·실패한다.
- **schedule에 공개할 개념**: 관리자(직원 소속)와 기사를 서로 다른 ID로 제공한다. schedule은 기사를 조직과 맺은 기사 계약(Technician)으로 참조한다([schedule 구현 결정](schedule.md#schedule-implementation)).
- **총관리자 표현**: 총관리자는 직원 소속의 총관리자 표시로 나타내고 여러 명을 둘 수 있다([조직·계정] §4, ORG-010). 조직은 총관리자를 단일 참조로 가리키지 않으므로 조직과 최초 소속 사이의 순환 참조가 없다. 같은 발주사의 활성 직원 소속만 지정할 수 있고, 마지막 1명은 해제·비활성화할 수 없다. 별도의 중간 관리자 역할은 두지 않는다.
- **역할 변경 행 규칙**: 회원·발주사마다 직원 소속 1행, 기사 계약 1행까지 두고 활성은 둘 중 하나만 허용한다(두 저장소에 걸친 규칙이라 Application이 검증). 상태는 [조직·계정] §9대로 활성·비활성 둘뿐이며, 역할을 바꾸면 기존 활성 행을 비활성으로 바꾸고 대상 행은 없으면 만들고 있으면 재활성화한다. 그래서 기사 계약 ID가 유지되어 schedule의 배정·작업 이력이 이어진다. 역할 변경으로 끝난 행을 따로 표시하지 않으므로(변경 이력 화면이 없음) 참여 인원·소속 목록은 계정·발주사마다 한 줄만 보인다 — 활성 행이 있으면 그 행, 없으면 상태 변경 시각이 가장 늦은 비활성 행. 재활성화는 반대쪽에 활성 행이 있거나 대상이 목록에 보이는 행(마지막 역할)이 아니면 거부한다. 총관리자 소속은 역할 변경 대상이 아니다([조직·계정] §4.1). 참여 요청 승인도 이 행 규칙을 따른다(구현) — 비활성 행만 있는 신청자는 확정 유형 쪽 행을 되살리고 없으면 만들며, 확정 유형이 마지막 역할과 다르면 세부 유형을 해제하며, 총관리자 표시는 언제나 끈다([조직·계정] §6). 참여일은 행마다 `joined_at`에 두고(감사 컬럼 `created_at`과 별개) 다른 역할 행을 새로 만들 때 이전 참여일을 이어받는다.
- **유형 소프트 삭제**: 직원·기사·작업 유형은 삭제 여부·삭제 시각으로 소프트 삭제하고 복구·비활성화는 없다([조직·계정] §7). 이미 삭제된 유형의 재삭제는 성공으로 처리하고, 삭제된 유형의 지정은 거부한다. 이름 중복은 같은 발주사·같은 종류의 삭제되지 않은 유형끼리만 검사하고, DB에는 삭제되지 않은 행끼리의 (발주사, 이름) 부분 유일 인덱스를 둔다. 직원·기사 유형을 지우면 같은 트랜잭션에서 그 유형이 지정된 직원 소속·기사 계약을 "유형 없음"으로 해제한다. 직원·기사 유형은 소속·계약 도메인에 없어 Entity의 유형 컬럼만 매핑하고, 유형 삭제는 벌크로, 재참여 승인은 저장 어댑터가 해제한다. 둘 다 발주사를 잠근 뒤 바꾸므로 삭제된 유형이 되살아나지 않는다. 작업 유형은 행을 지우지 않고 이름·색상을 남겨 작업중·완료·취소 작업이 삭제 직전 라벨을 계속 보이고, 삭제하면 같은 트랜잭션에서 schedule이 시작 전 작업(등록·배정됨·작업전)만 유형 없음으로 바꾼다(요구 인터페이스 `WorkTypeRelease`). 작업에 유형을 지정하는 쪽의 선택 가능 확인은 유형 행을 공유 잠금으로 읽고, 삭제는 유형 행을 바꾼 뒤 해제해 둘이 한 줄로 선다. 직원·기사 유형 삭제 시 보존 규칙은 O-33.

| 소유 애그리게잇 | **Profile**(Root) — auth가 발급한 계정 식별자(값으로만 보관)·이름·연락처·가입 상태·가입일·탈퇴 시각·탈퇴 사유·마케팅 동의, 약관 동의 이력(종류·버전·시각, 추가만). 탈퇴하면 이름·연락처를 지움 |
| 관계 | `auth` → 참조 (웹 어댑터가 `AccountPrincipal` 사용, 탈퇴 서비스가 `AccountClosure` 호출, Conformist — auth는 profile을 조회·구독하지 않음) · 다른 모듈 API ← 가입 공통 검사(웹 계층, 모듈 의존 아님) · 다른 모듈 ← 이름 조회 계약 `ProfileLookup` 제공(소비자: organization 승인 대기 목록의 신청자 이름·참여 인원 목록의 이름, 계획: schedule 기사 이름, HM-288) · `organization`·`schedule` ← 요구 인터페이스 `WithdrawalBlocker` 구현(탈퇴 차단 판정)과 이벤트 `AccountWithdrawn` 구독(탈퇴 뒤처리) — 연결 예정 HM-319·HM-320 |

## 미해결 설계 이슈

모듈 경계·모델링에 관한 레포 쪽 결정만 둔다. 제품 결정이 필요한 항목은 각 BC의 차이·공백에 둔다.

| # | 이슈 | 비고 |
| --- | --- | --- |
| BC-002 | 참여 요청(MembershipRequest)을 `organization`에서 분리할 시점 | 현재는 승인·소속 생성의 원자성 때문에 `organization`에 둠 — 요청 생명주기가 복잡해지면 분리 검토 |

개인 계정·프로필 관리(마이페이지, 탈퇴)의 소유 컨텍스트(구 BC-001)는 2026-10-07 `auth`가 아닌 새 모듈로 정하고 2026-10-10 이름을 `profile`로 확정해 닫았다. `member`는 schedule의 조직 구성원 용어·organization의 `Membership`과, `account`는 auth의 `Account`와 겹쳐 쓰지 않았다. 결정 배경은 [ADR-001 인증과 계정](../adr/001-backend-architecture.md#인증과-계정), 모듈 내용은 [Profile](profile.md#profile)에 있다. 정산 포함 여부(구 BC-004)는 [작업] §13에서 MVP 제외로 정해졌고 탈퇴 차단 조건([조직·계정] §5.1)에도 정산이 없어 닫았다. 조직 간 일정 충돌(구 BC-005)은 제품 결정이라 schedule 차이(S-31)로 옮겼고, [스케줄·배정] §8(SCH-011)이 같은 발주사 안에서만 판정하기로 정해 닫았다.
