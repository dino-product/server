# Profile 모듈

- 기준일: 2026-10-10
- 기획 원본: [기획 원본 색인](../planning/README.md#baseline)의 [조직·계정] 정책서·기능명세. 표기(`[조직·계정] §5`)·차이 ID는 색인을 따른다
- 다른 컨텍스트와의 관계: [바운디드 컨텍스트 지도](bounded-contexts.md#profile)

이 문서는 `profile`의 책임·구현 결정·가입 공통 검사·연동 관계와 Notion 기획과의 차이를 소유한다. 제품 규칙(이름·연락처 입력 규칙, 가입 미완료 계정이 쓸 수 있는 기능, 약관 종류)은 다시 적지 않고 절 번호로만 참조한다. 모듈 목록·허용 의존성은 [도메인 지도](README.md#모듈별-책임과-공개-계약), 작업 지침은 [profile 지침](../../src/main/java/com/orbit/profile/AGENTS.md)이 원본이다.

## 책임과 범위

계정의 가입 프로필(이름·연락처), 가입 상태와 가입일, 약관 동의 이력과 마케팅 수신 동의를 소유하고, 가입을 마치지 않았거나 필수 약관 재동의 전인 계정이 가입 마무리에 필요한 API 밖을 쓰지 못하게 막는다. 계정 식별자 발급·외부 식별·토큰은 [auth](auth.md), 조직 소속·역할은 organization이 소유한다. profile은 auth가 발급한 계정 식별자를 값(`AccountId`)으로만 보관한다.

현재 구현 범위는 프로필 입력·수정, 필수 약관 동의(가입 완료)·재동의, 내 정보와 가입 단계 조회, [가입 공통 검사](#profile-signup-gate)다. 탈퇴, 프로필 사진, 마케팅 동의 단독 변경, 다른 모듈에 주는 공개 계약은 아직 없다([남은 일](#profile-todo)).

## 가입 상태와 이용 가능 판정

제품 규칙: [조직·계정] 정책 §5(가입 미완료 계정)·§5.1(필수 약관 재동의)·§9(계정 상태), 기능명세 §6(상태 전이).

- **가입 미완료는 행이 없는 것으로 시작한다**: 카카오 인증만 마친 계정은 프로필 행이 없고 가입 미완료(`PENDING_SIGNUP`)로 본다. 처음 프로필을 저장할 때 `PENDING_SIGNUP` 행을 만들고, 필수 약관에 모두 동의하면 `ACTIVE`가 되며 그 시각을 가입일로 남긴다. 프로필 저장은 가입 상태를 바꾸지 않는다.
- **이용 가능 = `ACTIVE` ∧ 필수 약관마다 마지막 동의 버전이 시행 버전**: 필수 약관이 개정되면 `ACTIVE` 계정도 재동의 전까지 가입 미완료와 같은 범위만 쓰므로 상태값만으로 판정하지 않는다. 선택 약관(마케팅)의 개정은 이용을 막지 않는다. 시행 버전의 원본은 [설정](#설정)이다.
- **다음 단계**(`nextStep`): 아직 마치지 않은 단계다. 프로필이 없으면 `PROFILE`, 프로필은 있으나 이용 불가면 `TERMS`, 이용 가능하면 `COMPLETED`. 변경 API도 저장 뒤의 단계를 같은 응답 모양으로 돌려준다. 다시 시작할 화면은 이 값만으로 고르지 않는다 — 가입 미완료 계정이 다시 로그인하면 입력해 둔 값이 채워진 프로필 입력 화면부터 시작해 "완료" 뒤 약관 동의로 이어진다([조직·계정] 정책 §5).
- **동의 이력은 추가만 한다**: 약관마다 종류·버전·동의 시각을 한 줄씩 남기고 고치거나 지우지 않는다. 시행 버전에 이미 동의한 필수 약관은 다시 기록하지 않는다. 마케팅은 동의 여부와 마지막 변경 시각을 따로 두고, 동의로 바꿀 때만 마케팅 약관 버전을 이력에 더한다. 약관 동의 요청에 마케팅 값을 보내지 않으면 기존 값을 두며 처음 가입이면 미동의로 시작한다.
- **동시 저장**: 같은 계정의 프로필 저장과 약관 동의가 겹치면 버전 열로 늦은 쪽을 `COMMON-409`로 거부해 먼저 저장된 가입 상태를 되돌리지 않는다. 첫 프로필을 동시에 만들 때의 기본 키 충돌도 같은 오류다.
- 상태 코드값은 Notion 제안값을 따른다(ORG-002, organization 쪽 [O-31](bounded-contexts.md#organization-gaps)). 탈퇴 상태 `WITHDRAWN`은 탈퇴 기능과 함께 추가한다.

## HTTP

모든 경로는 본인 계정만 다룬다. 경로의 계정이 요청자와 다르면 존재를 드러내지 않도록 `PROFILE-002`(404)로 거부한다. 응답은 세 API 모두 계정 식별자·가입 상태·다음 단계·이름·연락처·가입일·마케팅 동의 여부를 담는다.

| 요청 | 하는 일 | 제품 규칙 |
| --- | --- | --- |
| `GET /api/v1/profiles/{accountId}` | 내 정보와 가입 단계. 프로필이 없으면 `PENDING_SIGNUP`·`PROFILE` | [조직·계정] 정책 §5·§5.1, 기능명세 §7 |
| `PUT /api/v1/profiles/{accountId}` | 프로필 입력(없으면 가입 미완료 프로필 생성)·수정 | [조직·계정] 정책 §5(입력값·이름 공통 입력 규칙)·§5.1·§11, 기능명세 §5·§9 |
| `POST /api/v1/profiles/{accountId}/terms-agreements` | 필수 약관 동의(가입 완료)·재동의, 마케팅 값을 보내면 함께 반영 | [조직·계정] 정책 §5(약관 동의)·§5.1, 기능명세 §5 |

- 오류: `PROFILE-001`(입력 규칙 위반, 400), `PROFILE-002`(다른 계정, 404), `PROFILE-003`(프로필 입력 전 약관 동의, 409), `PROFILE-004`(필수 약관 미동의, 400), `PROFILE-005`(가입 미완료·재동의 전 이용, 403, [공통 검사](#profile-signup-gate)), 동시 저장 충돌 `COMMON-409`.
- 이름·연락처 규칙은 Domain 값객체가 한 번만 검사하고 서비스가 `PROFILE-001`로 바꾼다. 요청 본문에 같은 제약을 두지 않는다.

## 가입 공통 검사

제품 규칙: 가입 미완료·재동의 전 계정이 쓸 수 있는 기능은 [조직·계정] 정책 §5(가입 미완료 계정)·§5.1, 기능명세 §8.

```text
Authorization: Bearer {accessToken} → /api/** (허용 목록 제외)
  → AccessTokenAuthenticationFilter (auth, 무효 토큰은 여기서 404로 끝남)
  → DispatcherServlet → SignupGateInterceptor.preHandle (컨트롤러 메서드로 연결된 요청만)
  → CheckServiceAccessUseCase → 이용 불가면 PROFILE-005(403)
```

- **등록과 허용 목록**: `ProfileWebConfig`(`WebMvcConfigurer`)가 인터셉터를 `/api/**`에 걸고 `/api/v1/profiles/**`, `/api/v1/auth/**`를 뺀다. 인증되지 않은 요청은 인가 단계가 이미 걸렀거나 공개 경로이므로 넘긴다. 공개 API도 토큰을 붙여 부르면 인증된 요청이라 검사한다(2026-10-10 결정). 가입 전에 써야 하는 API(링크·QR 회사 확인 HM-289, 탈퇴)는 공개 여부와 관계없이 허용 목록에 더한다.
- **보안 필터가 아니라 인터셉터인 이유**: 보안 필터로 두면 없는 경로도 403이 되어 auth의 "폐기·만료·위조 토큰의 404는 실제로 없는 자원의 404와 같다" 계약([Auth 인증 흐름](auth.md#인증과-로그아웃-흐름))이 깨진다. 인터셉터는 컨트롤러 메서드로 연결된 요청만 보므로 없는 경로는 그대로 404가 된다.
- **다른 모듈 영향**: 다른 모듈은 검사를 직접 넣지 않으며 허용 목록 밖의 새 API는 자동으로 검사 대상이 된다. 허용 목록은 다른 모듈의 URL 문자열이라 모듈 의존이 아니고 `ModularityTest`가 보지 못하므로, auth API를 `/api/v1/auth/**` 밖에 두거나 가입 전 API를 더할 때 허용 목록을 직접 고친다.
- **테스트 영향**: 다른 모듈의 `@ApplicationModuleTest`에는 profile이 올라오지 않아 이 검사가 빠진다. 전체 컨텍스트 API 통합 테스트에서 실제 Access Token으로 인증 요청을 보내려면 계정이 가입을 마쳐야 하며, `src/test/java/com/orbit/support/SignupTestSupport`가 실제 API로 로그인·프로필 입력·필수 약관 동의를 마친다.
- **OpenAPI**: 다른 모듈의 ControllerDocs는 profile 오류 타입을 선언할 수 없으므로 `SignupGateOpenApiCustomizer`가 허용 목록 밖의 Bearer 인증 연산마다 403 `PROFILE-005` 응답과 예시를 덧붙인다. 각 ControllerDocs에는 선언하지 않는다.

## 저장 모델

- `profiles`: 기본 키 `account_id`(auth가 발급한 계정 식별자), 이름, 연락처(숫자만), 가입 상태, 가입일, 마케팅 동의 여부·변경 시각, 낙관적 잠금용 `version`. 연락처는 계정 사이에 중복을 허용하므로 유일 제약이 없다.
- `profile_terms_agreements`: 계정별 약관 종류·버전·동의 시각. 추가만 한다.
- auth의 `accounts`로 가는 외래 키는 두지 않는다(모듈 경계). 두 테이블의 스키마 마이그레이션은 auth와 마찬가지로 아직 없다([실행 프로필 규칙](../../.claude/skills/dino-architecture/references/persistence.md#profiles)).

## 연동 관계

- **auth (현재)**: 컨트롤러와 공통 검사가 auth 루트 계약 `AccountPrincipal`에서 계정 식별자만 받아 Command·Query에 넘긴다(Conformist). 이 의존 때문에 auth는 profile을 조회·구독할 수 없고, auth에 무언가를 시켜야 하면 profile이 auth 공개 계약을 직접 호출한다. 로그인 응답에는 가입 단계가 없으므로 클라이언트는 로그인 뒤 `GET /api/v1/profiles/{accountId}`로 확인한다.
- **계획된 관계** (현재 허용 의존성이 아님):
  - 다른 모듈(예: schedule의 기사 이름 표시)이 계정 식별자로 이름을 조회하는 계약 — HM-305에서 추가한다.
  - 탈퇴 때 토큰 폐기·외부 식별 해제는 profile이 auth 공개 계약을 직접 호출한다(auth가 profile 이벤트를 구독하면 순환). 탈퇴 차단 판정은 profile이 판정 인터페이스를 두고 organization·schedule이 구현하는 방향이며 HM-254에서 합의한다.
  - organization의 링크·QR 회사 확인 API(HM-289)는 경로가 정해지면 허용 목록에 더한다.

## 공개 계약

없음(이름 조회 계약은 HM-305 모듈 연동 PR에서 추가 예정). 다른 모듈은 profile 타입을 참조하지 않는다. 가입 공통 검사는 공개 계약 없이 웹 계층에서 다른 모듈 API에 적용된다.
