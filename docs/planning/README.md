# 기획 원본 색인

제품 결정(누가·무엇을·언제, 사용자가 체감하는 제한·표시)의 원본은 Notion 기획 문서다. 레포는 제품 규칙을 다시 적지 않고 **기준 버전·절 참조·구현 결정·차이**만 관리한다. 판단 기준은 "기획자나 사용자가 보면 달라지는가?"이며, 달라지면 Notion, 달라지지 않으면 레포가 원본이다.

| 구분 | 원본 | 예 |
| --- | --- | --- |
| 제품 결정 | Notion 정책서·기능명세 (아래 표) | 권한, 작업 시작 가능 시간, 취소·거절 사유 목록, 결제 방식, 사진 개수·용량, 입력 제한 |
| 구현 결정 | 모듈 공통 규칙은 각 BC 문서의 구현 결정 절, 유즈케이스 하나에만 해당하는 판단은 Javadoc·PR 기술적 선택 (모듈별 문서 예: [schedule](../domain/schedule.md#schedule-implementation), 아직 분리하지 않은 BC는 [바운디드 컨텍스트 지도](../domain/bounded-contexts.md#bounded-contexts)) | 잠금, 배정 이력 구조, 멱등 처리, 시각 정밀도, 오류 코드 |
| 둘 사이의 차이 | 각 BC 문서의 차이·공백 절 | Notion과 구현이 다른 것, 구현 중 생긴 제품 결정 필요 항목 |

## 기준 문서

모든 문서는 Notion [기획 문서 DB](https://app.notion.com/p/3cdf190e116680a7af2deda1422b4c95)(데이터 소스 `collection://3cdf190e-1166-80c1-859c-000b9854dd59`)에 있다. 링크는 페이지 단위로만 걸고 절은 `§번호`로 적는다. 버전이 올라도 페이지 주소는 그대로이고 제목 끝의 버전만 바뀌므로(새 페이지를 만들지 않음) 링크는 이 색인에서만 관리한다. 작업 계획·PR·이슈에는 이 색인의 링크로 정책서와 기능명세의 절을 적는다(예: `[작업] 정책 v1.1 §10`, `[작업] 기능명세 v1.1 §4`).

- **기준 버전**: 그 버전까지의 변경을 레포가 확인해, 구현했거나 BC 문서의 차이·공백에 등록했다는 뜻이다. 그 버전대로 구현이 끝났다는 뜻이 아니며, 구현 반영 여부는 차이·공백이 보여 준다.
- **확인 시각**: 그 문서를 마지막으로 Notion과 대조한 시각(KST, 분 단위 `YYYY-MM-DD HH:MM`)이다. 같은 날 뒤이어 고친 수정도 잡도록 날짜가 아닌 시각으로 적는다. 문서마다 따로 두며, 한 문서를 동기화해도 다른 문서의 확인 시각은 바꾸지 않는다. 대조를 시작한 시각을 적는다(끝난 시각을 적으면 그 사이의 수정을 놓친다).

초기 기준선의 확인 시각은 18개 문서의 버전·수정 시각을 함께 재확인한 시각이다(본문 대조는 2026-09-30, 모든 문서의 최종 수정은 그 이전).

## 동기화 상태 확인

레포가 반영한 기준 버전과 Notion 최신 문서를 비교한다. 착수와 로컬 리뷰가 같은 절차를 쓴다. 에이전트의 Notion 연결(Claude Code의 Notion 커넥터, Codex의 Notion 플러그인)로 읽으며 개인 토큰을 두지 않는다. CI는 Notion을 읽지 않는다.

- **언제**: 세션에서 제품 동작을 바꾸는 작업을 처음 시작할 때와 동기화 작업 전에 한 번. 같은 세션의 다음 작업은 결과를 재사용하고, 다른 모듈로 넘어가면 그 모듈 문서만 추가로 본다. 리팩터링·테스트 보강처럼 제품 동작이 바뀌지 않는 작업은 확인하지 않는다.
- **무엇을 읽나**: 버전 비교는 본문 없이 검색 결과로 한다. 본문은 이번 작업이 참조하는 절이 있는 문서와, 판정이 `밀림`·`이력 없는 수정`인 문서의 변경 이력만 연다.
- **본문은 요약으로 받는다**: Notion 연결은 절 단위로 읽지 못해 페이지 전체(문서당 1만 토큰 이상)를 가져온다. Notion 연결을 쓰는 하위 에이전트가 있으면(예: Claude Code의 하위 에이전트) 본문 읽기를 맡기고, 필요한 절의 원문 요지·기준 버전 이후 변경 이력 행·관련 QA 시나리오만 받는다. 없으면 직접 읽고 같은 형식으로 요약해 세션 안에서 재사용한다.

1. **버전 비교(가벼움)**: 기획 문서 DB 데이터 소스를 범위로 `정책 기능명세 QA 시나리오`를 검색한다(하이라이트 끔, 결과 수 50). 결과의 제목 끝 버전(`[현장 수행] 정책 v1.1`)을 위 표의 기준 버전과, 수정 시각(`timestamp`, KST로 환산해 분 단위)을 그 문서의 확인 시각과 비교한다. 대상 모듈 문서가 결과에 빠져 있으면 그 문서만 직접 연다. 연결이 데이터 소스 범위 검색을 지원하지 않으면(예: Codex의 Notion 플러그인) 문서 제목(`[현장 수행] 정책`)으로 검색하거나 색인의 링크로 페이지를 열어 같은 두 값을 확인한다.
2. **변경 이력(필요할 때만)**: `밀림`·`이력 없는 수정` 문서를 열어 본문 `## 변경 이력` 표(버전·시점·변경 내용·사유)에서 기준 버전보다 새 행만 추린다. 본문의 "상태 변경 이력" 같은 절·표 셀과 헷갈리지 않게 이 제목 바로 아래 표만 쓴다.
3. **영향 찾기**: 추린 행의 절 번호(`§5`)·이슈 ID(`FLD-007`)를 인용하는 BC 문서 행과 그 행의 차이 ID를 찾는다. 절 번호·이슈 ID가 없으면 본문 대조가 필요하다고 적는다.
4. **작업 절 읽기**: 이번 작업이 참조하는 정책서·기능명세 절의 원문 요지를 받는다. QA·시나리오는 새 동작을 추가하거나 규칙을 바꿔 새 테스트 케이스를 설계할 때만 같은 도메인 문서의 관련 시나리오를 본다(기존 동작을 유지하는 수정에는 열지 않는다).
5. **보고**: 모두 `최신`이면 "기획 버전 확인: schedule 관련 12개 최신" 한 줄로 끝낸다. 그 밖의 판정은 아래 표의 용어로 문서·미반영 변경 이력·영향 차이 ID를 보고한다. 하위 에이전트에 위임할 때는 판정과 관련 절의 적용 내용을 인계한다(하위 에이전트는 Notion 연결이 없을 수 있다).

어느 경로로도 Notion을 읽지 못하면 해당 문서를 `확인 불가`로 보고하고 원인(연결 없음·권한 없음·네트워크 차단)을 적는다. 변경 이력의 원본은 각 Notion 문서의 `## 변경 이력` 표다.

| 판정 | 뜻 | 할 일 |
| --- | --- | --- |
| 최신 | 기준 버전 = Notion 버전, 확인 시각 뒤 수정 없음 | 그대로 진행 |
| 밀림 | Notion 버전이 더 높음 | 구현 전에 알리고 [동기화](#sync)를 별도 커밋으로 먼저 한다. 바뀐 규칙이 진행 중인 구현에 걸리면 멈추고 확인받는다 |
| 이력 없는 수정 | 버전은 같은데 확인 시각 뒤에 수정됨 | 참조 절을 원문과 대조한다. 영향이 없으면 그 문서의 확인 시각만, 있으면 차이·공백과 확인 시각을 동기화 커밋으로 갱신하고, 버전·변경 이력 없이 바뀐 사실을 기획에 알린다. 구현은 막지 않는다 |
| 색인 오류 | 기준 버전이 Notion보다 높음 | 색인을 바로잡는다 |
| 확인 불가 | Notion 연결 없음, 권한 없음, 제목에 버전 없음 | 확인하지 못한 범위를 보고하고, 레포의 절 참조·차이·공백까지만 근거로 삼는다 |

## 동기화 규칙

- **Notion 버전이 오르면** 그 문서의 기준 버전·확인 시각과 영향받는 BC 문서의 제품 규칙 참조(절 번호)·차이·공백을 함께 고친다. 바뀐 제품 규칙을 레포 본문에 옮겨 적지 않는다. 변경 이력 표의 기준 버전 이후 행을 근거로 삼는다.
- **동기화는 기능 변경과 섞지 않고 별도 커밋**으로 한다. 레포 쪽 반영 기록은 이 커밋 이력이 맡으므로 Notion 변경 이력을 레포에 옮겨 적지 않는다. 커밋 형식:

  ```text
  docs(planning): [현장 수행] 정책 v1.1→v1.2 동기화

  - v1.2 §5 시작 가능 시간 변경 → S-02 갱신
  - v1.2 §8 문구 수정 → 영향 없음
  ```

- **구현 중 제품 결정이 필요하면** 해당 BC의 차이·공백에 적고 [기획 결정 요청](#plan-request)으로 기획에 올린다. 요청 메시지 링크를 추적 칸에 적고, 기획이 정책서 "확정 필요 항목"에 등록하면 그 ID로 바꾼다. 요청 전에는 `미등록`으로 둔다. 레포에서 임의로 확정하지 않는다. 차이·공백 항목의 구현 여부는 [대역별 구현 규칙](#gap-actions)을 따른다.
- **Notion과 구현이 다르면** 구현 수정을 맡은 작업(Jira 티켓 등)이 생길 때 추적 칸에 적는다.
- **차이가 해소되면** 행을 지운다. 제품 결정은 Notion에, 그 결정을 구현하는 방식은 모듈 공통 규칙이면 BC 문서의 구현 결정 절에 남긴다. 기능 PR이 행을 해소하거나 새로 만들면 같은 PR에서 BC 문서를 고친다.
- Notion 원문은 [동기화 상태 확인](#status)의 Notion 연결로 읽는다. 연결이 없는 환경은 레포의 절 참조·차이·공백까지만 판단하고 확인하지 못한 범위를 보고한다.

<a id="gaps"></a>
## 차이·공백 표기

각 BC 문서(예: [schedule](../domain/schedule.md#schedule-gaps))의 제품 규칙 참조·차이·공백 표는 아래 표기를 공유한다.

- **제품 규칙 참조의 차이 칸**: `—`는 Notion 절과 현재 구현을 대조해 일치함, `미구현`은 대조할 구현이 아직 없음, ID는 해당 차이·공백 행을 뜻한다. 대조하지 않은 행은 비워 두지 않고 `미대조`로 적는다.
- **ID 대역**: 모듈 접두사(`S` schedule, `O` organization 등) 뒤에 `0x` Notion 확정·구현이 다름 / `1x` 구현에서 정한 제품 결정·Notion 결정 필요 / `2x` Notion 확정·미구현 / `3x` Notion도 미정. 분류가 바뀌면 새 대역의 번호로 옮기고 옛 번호는 재사용하지 않는다.
- **추적 칸**: Notion 정책서 "확정 필요 항목"의 ID(예: `JOB-007`), [기획 결정 요청](#plan-request)의 Slack 메시지 링크, 구현 수정을 맡은 작업 중 하나를 적는다. `미등록`은 아직 아무 곳에도 올리지 않았다는 뜻이다.

<a id="gap-actions"></a>
**대역별 구현 규칙** — 차이·공백 항목을 다룰 수 있는지는 Notion에 확정된 기준이 있는지로 정한다.

| 대역 | 해소를 요청받았을 때 | 다른 작업 중 마주쳤을 때 |
| --- | --- | --- |
| `0x` Notion 확정·구현이 다름 | Notion 기준에 맞춰 구현하고 행을 지운다 | 고치지 않고 알린다(요청 범위 밖) |
| `2x` Notion 확정·미구현 | Notion 기준으로 구현하고 행을 지운다 | 고치지 않고 알린다 |
| `1x` Notion 결정 필요 | 구현하지 않고 [기획 결정 요청](#plan-request)으로 넘긴다 | 현재 동작을 유지하고 넓히지 않는다 |
| `3x` Notion도 미정 | 구현하지 않고 [기획 결정 요청](#plan-request)으로 넘긴다 | 현재 동작을 유지하고 넓히지 않는다 |

- `1x`·`3x`에 대해 개발자와 합의한 결정도 바로 구현하지 않는다. [기획 결정 요청](#plan-request)으로 기획이 Notion 정책서에 반영(확정 필요 항목 확정·버전 갱신)한 뒤 레포를 [동기화](#sync)하고 구현한다. 결정이 Notion에 오르면 행은 `0x`·`2x`로 옮겨지거나 해소된다.
- 해소하면서 Notion에 없는 판단이 새로 필요하면, 사용자에게 보이지 않는 것(오류 코드·저장 방식 등)은 구현에서 정하되 모듈 공통 규칙일 때만 BC 문서의 구현 결정 절에 적고(그 밖은 Javadoc·PR 기술적 선택), 사용자가 체감하는 것(경계값·문구·권한 등)은 새 `1x` 행으로 올리고 [기획 결정 요청](#plan-request)을 한다.

<a id="plan-request"></a>
## 기획 결정 요청

Notion에 없는 제품 판단(`1x`·`3x`, 구현 중 새로 생긴 사용자 체감 판단)은 레포나 대화에서 확정하지 않고 기획이 Notion에 반영한다. Notion 반영은 기획이 하고, 개발자·에이전트는 Notion을 직접 고치지 않는다.

1. **합의**: 작업 계획 단계에서 개발자와 이번 작업 범위에 필요한 판단을 끝까지 합의한다. 범위 밖의 판단은 올리지 않는다.
2. **요청 초안**: Slack `#plan` 채널(`C0BS2ACANVC`)에 보낼 메시지를 쓴다. 한 메시지에 아래를 담는다.
   - 대상 문서와 절(예: `[작업] 정책 v1.1 §10`)
   - 결정할 질문 한 줄과 개발자와 합의한 제안 결정
   - 검토한 선택지와 근거(짧게)
   - 영향: 차이 ID(`S-12`), 이슈 키, 이 결정을 기다리는 작업
3. **게시**: 초안을 개발자에게 보여 확인받은 뒤 게시한다. Slack 연결이 없으면 본문만 출력해 개발자가 직접 보낸다. 게시한 메시지 링크를 차이·공백의 추적 칸과 작업 계획에 적는다.
4. **보류**: 그 기능의 구현은 Notion에 반영될 때까지 시작하지 않는다. 작업 계획에는 `노션 반영 대기`로 표시한다.
5. **재시도**: 기획이 Notion을 고치고 버전을 올리면 개발자가 작업을 다시 시작한다. [동기화 상태 확인](#status)이 `밀림`으로 판정하면 [동기화](#sync) 커밋으로 행을 옮기거나 지운 뒤 구현한다.

## 용어 대응

레포 문서는 Notion 표시값을 쓰고, 코드 식별자는 백틱으로 적는다. 옛 표현은 코드 주석·이전 문서에 남아 있을 수 있으며 같은 뜻이다.

| Notion 표시값 | Notion 코드(제안) | 레포 코드 | 옛 표현 |
| --- | --- | --- | --- |
| 등록 (기사·시간 없으면 대기함) | `REGISTERED` | `REGISTERED` | 대기중 |
| 배정됨 | `PENDING_ACCEPT` | `PENDING_ACCEPTANCE` | 수락대기 |
| 작업전 | `ACCEPTED` | `ACCEPTED` | 수락됨 |
| 작업중 | `IN_PROGRESS` | `IN_PROGRESS` | — |
| 완료 | `COMPLETED` | `COMPLETED` | — |
| 취소 | `CANCELED` | `CANCELLED` | — |

| Notion 용어 | 레포 이름 | 비고 |
| --- | --- | --- |
| 작업 (Job) | `Work` | 애그리게잇명은 Work로 통일 |
| 발주사 | 조직, `Organization` | |
| 소속 | `Membership` | 총관리자·직원의 조직 소속 |
| 기사 (기사 소속) | 기사 계약, `Technician` | schedule은 기사를 소속이 아닌 기사 계약 ID로 참조 |
| 총관리자 / 직원 | `OWNER` / `STAFF` (`ActorRole`) | 직원 유형은 권한에 쓰지 않음 |
| 대기함 | Backlog (조회 모델) | 상태가 아니라 조회 조건 |
| 리스케줄 | 일정 변경 (`Reschedule`) | |
| 배정 해제 | `Unassign` | |
