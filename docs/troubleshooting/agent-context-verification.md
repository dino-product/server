# 지침 변경 뒤에도 하위 규칙이 빠지거나 출력이 잘리는 경우

## 증상과 확인된 한계

- 실행·검사·커밋의 참조 경로가 사람용 온보딩이나 여러 작업 단계의 통합 문서로 이어지면 무관한 내용을 함께 읽을 수 있습니다. 파일을 나누기만 하면 직접 진입 절 밖에 있는 공통 규칙을 놓칠 수도 있습니다.

- 루트에서 시작해 모듈 지도를 읽어도 다른 모듈로 작업이 확대될 때 하위 `AGENTS.md` 본문을 누락할 수 있습니다. 링크·파일 목록을 보거나 모델이 규칙을 요약한 것만으로 본문 로딩과 실제 준수를 입증할 수 없습니다.
- 내부 실행 도구의 출력 한도를 늘려도 상위 도구 응답의 한도 때문에 실패 로그가 잘릴 수 있습니다. 테스트 성공이나 토큰 감소만으로 필요한 지침·오류를 모두 읽었다고 판단하지 않습니다.
- 여러 문서 조회 결과를 한 응답으로 합치면 중간의 커밋 지침 전체가 잘릴 수 있습니다. 조회 명령이 성공했어도 반환된 본문에 체크포인트가 없으면 상세 규칙을 읽은 근거가 되지 않습니다. 루트의 핵심 커밋 규칙이 이미 입력에 있었다면 상세 본문 누락과 실행 중 규칙 미준수를 구분합니다.
- 최종 테스트가 통과해도 중간 커밋의 Bean 조립이 실패하거나, mock이 대체한 실제 경계의 결함이 남을 수 있습니다. 커밋 개수와 AI가 나눠 읽은 묶음 수만으로 사람이 검토할 PR과 작은 커밋이 마련됐다고 판단하지 않습니다.
- 여러 행동의 Domain·Port·Service·Adapter를 계층별로 모두 작성한 뒤 검사하면, 작은 단위로 진행하겠다는 설명과 달리 첫 커밋까지 기능 전체가 누적될 수 있습니다. 선행 구현에 대한 의존성이나 공유 파일이 있다는 사실만으로 같은 커밋이 필요하다고 판단하지 않습니다.

## 진단과 대응

1. [지침 탐색 규칙](../../AGENTS.md#읽기-경로)에 따라 실제 수정 경로와 세션에 주입·조회된 지침을 대조합니다. 새로운 모듈의 첫 편집 전에 빠진 하위 지침을 읽고 해당 변경을 검토합니다. 단순 키워드 검색 결과와 본문 조회를 구분합니다.
2. 잘린 출력은 최종 응답 한도를 기준으로 누락 구간만 읽습니다. 긴 검사 로그는 임시 파일에 보존하고 종료 코드를 유지한 채 실패 요약을 출력하거나 기존 테스트 보고서의 관련 실패만 조회합니다. 세부 기준은 [검사 실행과 출력](../conventions/testing/execution.md#execution)을 따릅니다.
3. [새 세션 로딩 확인](../agents/context.md#에이전트-문서-탐색)과 실제 작업의 지침 준수를 따로 검증합니다. 누락이 반복되면 해결됐다고 보고하지 않고 수정 경로·본문 조회 여부·적용 행동을 근거로 남깁니다. 문구 보강만으로 준수가 자동 강제되지는 않습니다.
4. 완료 주장과 실제 diff·검사 범위를 대조합니다. 중간 커밋의 조립이 의심되면 그 상태를 분리해 필요한 검사를 실행하고, mock 바깥의 실패 조건은 [실제 경계 검사](../conventions/testing/design.md#design)로 확인합니다. 커밋·PR 분할은 [사람용 리뷰 기준](../conventions/workflow/review/procedure.md#procedure)으로 평가하며 원본 이력을 재작성해 결과를 보정하지 않습니다.

5. 문서량을 줄일 때는 `AGENTS.md`의 작업 상황에서 실제 진입 절까지 경로를 따라갑니다. 단계별 원본·앵커를 연결하고 출처·이전 절로 돌아가는 링크를 다음 읽기 지시와 구분합니다. 앵커가 존재해도 안내한 내용이 그 절 안에 있는지 확인하며, 분할한 절에서 필요한 공통 규칙·승인·검증 조건을 찾을 수 있는지 확인합니다. 원문과 이동한 본문을 대조하고 링크를 검사하며, 파일 크기 감소를 실제 토큰 절감으로 보고하지 않습니다.
6. 커밋이 다시 커졌다면 [작업 중 커밋 체크포인트](../conventions/workflow/checkpoints.md#checkpoints)와 실제 도구 호출 순서를 대조합니다. 첫 편집 전 목적·범위·선행 의존성·집중 검사 계획, 다음 단위 편집 전 검증과 커밋, 커밋 실행 전 staged diff 검토가 있었는지 확인합니다. “구현·테스트·설정을 함께 포함한다”는 설명만으로 단위별 한 변경 이유가 정해진 것은 아닙니다. 커밋 금지 재현은 단위별 계획·검사만 평가하고 실제 커밋 분할을 검증했다고 보고하지 않습니다. `git diff --cached --stat` 출력과 `git commit`을 한 명령으로 이어 실행한 기록은 출력에 근거해 분리 여부를 판단한 증거가 아닙니다. 상세 지침 재조회 여부와 실제 행동의 개선을 따로 검증하며, 줄 수 제한이나 문구 추가만으로 재발이 해결됐다고 보고하지 않습니다.

## 개선 효과를 비교할 때

- 같은 프롬프트도 모델의 설계 제안과 후속 승인에 따라 기능 범위가 달라집니다. 실행 전에 기능 명세·금지/경계 조건·완료 기준을 고정합니다. 코드 기준점·모델·추론 수준·실행 방식·전역 목록을 맞추며 모델 비교처럼 의도적으로 바꾼 조건은 명시합니다.
- 평가용 회귀 검사는 모델이 제출한 테스트와 별도로 준비하고 결과에 맞춰 약화하지 않습니다. 요구조건→구현 위치→검사 사례→실제 결과를 연결하며, 설정·스키마 적용 준비와 미검증 경계도 비교합니다.
- 기능·안전성·계약과 검증 범위가 충족된 결과끼리 토큰·시간 효율을 비교합니다. 조건을 충족하지 못한 결과의 적은 사용량을 최적화 성공으로 판정하지 않습니다. PR 크기·커밋 이유·각 상태의 조립 근거를 함께 보고, 테스트 수와 커밋 수를 품질 점수로 바꾸지 않습니다.
- 공유 worktree는 다른 브랜치의 과거 해법도 노출합니다. 이전 답안을 배제해야 하는 실험은 필요한 기준 이력만 가진 독립 저장소에서 실행하고 답안 재사용 실행은 비교에서 제외합니다.
- 요청별 고유 사용량을 집계하고 재개 시 누적 카운터를 중복 합산하지 않습니다. 캐시 입력·비캐시 입력·출력·압축을 구분하며 단일 실행의 감소율을 순수 세팅 효과나 비용 절감률로 단정하지 않습니다.
- 원본 로그·수치·실험 이력은 별도 산출물에 두고 이 문서에는 재사용 가능한 진단만 유지합니다.
