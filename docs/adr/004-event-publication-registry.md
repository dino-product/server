# ADR-004: 이벤트 발행 기록과 알림 발신 보장

- 상태: Accepted
- 기준일: 2026-10-27
- 범위: 모듈 간 이벤트의 발행 기록·완료 보관·실패 재전송·멈춘 발행 처리와, 그 때문에 생기는 리스너·이벤트 계약 규칙, 메시지 브로커를 두지 않는 이유와 도입 기준, 기사 앱 푸시 발신 대기열. 실행 규칙은 [트랜잭션 이벤트](../../.claude/skills/dino-architecture/references/persistence.md#events)가 소유합니다. 알림을 누구에게 어떤 문구로 만들지와 푸시 제공자 선택은 범위 밖입니다([notification 문서](../domain/notification.md#notification-implementation)).

## 배경과 목적

모듈 간 이벤트는 변경 트랜잭션에서 발행하고 커밋 후 비동기 리스너로 소비합니다([ADR-001](001-backend-architecture.md#영속성과-이벤트)). 리스너가 실패하거나 처리 중에 인스턴스가 멈추면 이벤트가 그대로 사라졌고 다시 보낼 수단이 없었습니다. 알림은 다른 모듈의 이벤트를 받아 만들어지는데, [알림] 기능명세 v1.2 §10과 정책 v1.3 §1은 모든 트리거가 수신자에게 도달해야 한다고 정합니다. [메시지 브로커를 두지 않고](#메시지-브로커를-두지-않는-이유) PostgreSQL 안에서 이 보장을 만듭니다(HM-189 설계).

## 결정

- **Spring Modulith의 JDBC 발행 기록을 씁니다.** 이벤트를 발행한 트랜잭션 안에서 리스너마다 `event_publication`에 행을 남기므로, 커밋하면 기록도 남고 롤백하면 둘 다 없습니다. 이미 쓰는 `@ApplicationModuleListener`와 맞물리고 실패 발행 재전송 API가 있어 아웃박스 테이블과 폴러를 직접 만들지 않습니다.
- **모듈 리스너(`@ApplicationModuleListener`)로 가는 이벤트만 기록합니다**(`spring.modulith.events.registry-trigger-annotation`). Modulith 기본값은 커밋 후 리스너 전부를 기록합니다. 다시 보낼 의미가 있는 것은 별도 트랜잭션에서 비동기로 도는 모듈 리스너입니다. 모듈 리스너가 없는 이벤트는 기록되지 않으므로 이 테이블은 이벤트 저장소가 아닙니다.
- **처리를 마친 발행은 보관 테이블(`event_publication_archive`)로 옮기고 기한 없이 둡니다**(`completion-mode: archive`). 이벤트 원문은 각 모듈 테이블에 남지 않아서(예: `UserRegistered`는 로그만 남김) 지우면 무엇을 발행했는지 사라집니다. 기본값인 삭제와 같은 테이블에 완료 표시만 하는 방식을 검토했습니다. 정리 작업을 두지 않는 대신 이벤트에 개인정보를 넣지 않습니다.
- **실패한 발행은 처리될 때까지 횟수 제한 없이 다시 보냅니다**(`app.events.resubmission.*`, `shared.internal.event.FailedEventPublicationResubmitter`). 1분마다 실패 발행을 확인해, 마지막 시도 뒤 기다린 시간이 대기 시간을 넘은 발행만 보냅니다. 대기 시간은 1분에서 시작해 실패할 때마다 두 배로 늘고 30분에서 멈춥니다. 알림 미발신은 비용이 걸린 문제라 포기 상태를 두지 않습니다. 정해진 횟수 뒤 포기하는 안은 포기한 알림이 조용히 사라져 택하지 않았고, 대기 시간을 늘리는 것은 계속 실패하는 발행이 주기마다 리스너를 다시 돌리지 않게 하기 위해서입니다. Modulith는 실패 발행을 오래된 순으로 읽어서, 읽는 개수를 제한하면 기다리는 중인 옛 발행이 앞자리를 채워 보낼 때가 된 발행이 밀려납니다. 그래서 개수 제한 없이 읽고 대기 시간으로 거릅니다. HM-278 설계 DG-03의 "1분 지난 미완료 발행 전체 재제출"은 아직 처리 중인 리스너를 한 번 더 돌려 택하지 않았습니다.
- **멈춘 발행은 5분 뒤 실패로 바꿔 재전송 대상에 넣습니다**(`spring.modulith.events.staleness.*`, 1분마다 검사). 인스턴스 중단 등으로 대기·처리·재전송 중(PUBLISHED·PROCESSING·RESUBMITTED)에 머문 발행을 구합니다. 재기동 때 미완료 발행을 한꺼번에 다시 보내는 옵션(`republish-outstanding-events-on-restart`)은 여러 인스턴스가 같은 발행을 겹쳐 보내므로 끕니다.
- **같은 이벤트가 한 리스너에 두 번 이상 갈 수 있음을 받아들이고, 모듈 리스너를 멱등하게 만듭니다.** Modulith 2.1.1의 멈춤 판단은 최초 발행 시각 기준이라, 최초 발행에서 5분이 지난 발행은 재전송 직후 처리 중이어도 다음 검사에서 다시 실패로 바뀌어 한 번 더 실행될 수 있습니다. 여러 인스턴스가 함께 돌 때 재전송 표시(`STATUS != 'RESUBMITTED'` 조건부 갱신)는 같은 발행을 동시에 집는 일만 줄이고, 처리가 시작되거나 다시 실패한 뒤에는 앞서 목록을 읽은 다른 인스턴스가 또 보낼 수 있습니다. 커밋 `943e77e` 본문의 "한 인스턴스에만 넘긴다"는 이 보장보다 강한 표현입니다. 멈춤 기준을 30분으로 늘리는 안은 중단된 인스턴스의 발행 복구까지 늦추면서 중복을 없애지 못하고, 마지막 재전송 시각 기준으로 직접 검사하는 안은 Modulith 내부 테이블을 직접 다뤄 버전을 올릴 때 깨지기 쉽습니다. 재전송 방식에서 중복의 근본 대책은 멱등이므로 5분을 유지합니다.
- **처리되지 않은 발행은 `event_publication`에 FAILED로 남깁니다.** 상태·시도 횟수(`completion_attempts`)·마지막 재전송 시각(`last_resubmission_date`)으로 조회합니다. 지우거나 따로 옮기면 처리 완료를 보관하는 이유(이벤트 내용 보존)와 어긋납니다. 실패 건수를 Prometheus 지표로 내보내는 감시는 이 규모(관리자 1명 : 기사 30~50명)에 과해 두지 않습니다.
- **멈춤 검사 로거(`DefaultEventPublicationRegistry`)는 WARN으로 올립니다.** 멈춘 발행이 없어도 상태마다 INFO를 남겨 인스턴스마다 1분에 3줄이 쌓이기 때문입니다. 리스너 실패는 비동기 실행기가 ERROR로 남겨 그대로 보입니다. 같은 로거의 재전송 중 오류(INFO)는 함께 가려지지만, 그런 발행은 FAILED로 남아 `event_publication`에서 조회됩니다.
- **이벤트 record는 기록 행의 계약입니다.** 기록 행은 이벤트 타입 이름과 JSON 원문을 저장하므로 이벤트에는 식별자·상태·시각만 담고 이름·연락처 같은 개인정보는 넣지 않습니다. Modulith 2.1.1에서 이벤트 타입의 이름·패키지를 바꾸면 남은 행은 타입을 찾지 못해 재전송에서 빠진 채 기록 테이블에 남고 읽을 때마다 WARN 로그가 납니다. 필드 구조를 바꿔 역직렬화가 실패하면 그 발행만 30분 간격으로 계속 다시 보내져 실패하고 다른 발행의 재전송은 막지 않습니다. 그래서 바꾸기 전에 미완료 발행을 확인하거나 이전 타입을 남깁니다.
- **스케줄링은 `shared.internal.config.SchedulingConfig`가 직접 켭니다.** 지금은 spring-modulith-moments 자동 설정이 `@EnableScheduling`을 대신 켜고 있어서, 그 의존성이 빠지면 재전송과 멈춤 검사가 조용히 멈춥니다.

## 기사 앱 푸시 발신 대기열

이벤트 발행 기록은 "이벤트 → 알림 생성"까지 보장합니다. "알림 → 기사 앱 푸시"는 외부 제공자 호출이라 실패·중단이 잦고 오래 걸릴 수 있어 같은 PostgreSQL의 발신 대기열(`notification_deliveries`, `notification` 모듈)로 따로 보장합니다.

- **알림을 저장하는 트랜잭션에 발신 대기를 함께 넣고 주기 작업이 보냅니다.** 알림 서비스가 부르는 푸시 포트(`PushNotificationPort`)의 구현이 그 자리에서 보내지 않고 대기열에 넣으므로, 커밋되면 알림과 발신 대기가 함께 남고 롤백되면 함께 사라집니다. 리스너에서 바로 푸시를 부르는 안은 발신이 실패하거나 도중에 멈추면 다시 보낼 수 없고, 외부 호출 시간이 이벤트 처리를 붙잡아 택하지 않았습니다. 대상은 기사 앱 푸시뿐이며 총관리자·직원 알림은 웹 인앱(알림센터)이라 넣지 않습니다.
- **집기·발신·결과 저장을 나눕니다**(`app.notification.push-delivery.*`, 기본 5초마다 100건). 보낼 때가 된 행을 `FOR UPDATE SKIP LOCKED`로 집어 발신 중으로 표시하고 커밋한 뒤, 트랜잭션 밖에서 실제 발신 포트(`PushSender`)로 보내고, 결과를 새 트랜잭션으로 저장합니다. 여러 인스턴스가 함께 돌아도 같은 행을 동시에 집지 않고, 외부 호출이 DB 연결을 붙잡지 않습니다. 보내기 직전에 알림을 다시 읽어, 기다리는 동안 거절로 숨겨진 알림은 보내지 않습니다.
- **발신 중에 멈춘 행은 점유가 만료되면(기본 5분) 다시 집습니다.** 결과를 저장하기 전에 인스턴스가 멈추면 같은 푸시가 드물게 두 번 갈 수 있고, 이를 받아들입니다. 결과 저장은 집은 시점의 시도 횟수와 비교해, 점유가 만료돼 다른 인스턴스가 다시 집은 뒤 늦게 도착한 결과를 버립니다.
- **다시 보낼 실패는 횟수 제한 없이 재시도합니다.** 30초에서 시작해 실패마다 두 배, 최대 30분 간격이며, 실패한 발신들이 한꺼번에 몰리지 않도록 계산한 시간의 80~100%에서 고릅니다. 제공자 인증·설정 오류도 고치면 성공하므로 다시 보낼 실패입니다. 끝내는 것은 받을 기기가 없을 때(등록된 기기가 없거나 모두 등록 해제됨, SKIPPED, 알림센터의 알림은 남음, [알림] 정책 §5)와 요청 형식 오류처럼 다시 보내도 성공할 수 없을 때(FAILED)뿐입니다. 발신 하나는 수신 계정의 기기마다 보내고 한 기기라도 받으면 보낸 것으로 봅니다. 푸시 실패 처리는 기획 범위 밖의 기술 결정입니다([알림] 정책 NTF-002). 감시 지표는 두지 않고 행의 상태·시도 횟수·마지막 오류로 조회합니다.
- **푸시 제공자는 FCM입니다.** `PushSender`는 FCM HTTP v1 어댑터이고, FCM을 끈 `local`·`test`·`dev`만 보내지 않고 기록하는 발신기를 씁니다. 제공자 응답을 다시 보낼 실패·끝낼 실패·등록 해제로 나누는 규칙과 환경별 선택은 [notification 문서](../domain/notification.md#notification-implementation)가 원본입니다.

## 메시지 브로커를 두지 않는 이유

질문은 "알림이 애플리케이션 상태와 무관하게 저장소에 남아야 하는데 Redis·Kafka·RabbitMQ 없이 가능한가"였습니다. 가능하고, 브로커를 써도 PostgreSQL에 먼저 써야 합니다.

- **브로커는 저장소가 아니라 전달 수단입니다.** 알림 원본(목록·읽음 상태·이력)은 어떤 구성이든 DB에 있어야 합니다. DB 커밋과 브로커 발행은 한 트랜잭션이 아니어서 그 사이에 인스턴스가 멈추면 한쪽만 남습니다(이중 쓰기). 이를 막는 표준 해법이 같은 트랜잭션에 이벤트 행을 쓰는 DB 아웃박스이고, Modulith 발행 기록이 그것입니다. 그래서 PostgreSQL 단독이 브로커와 PostgreSQL을 함께 쓰는 구성보다 일관되고 운영할 저장소도 적습니다.
- **후보별 판단:**

  | 후보 | 판단 |
  | --- | --- |
  | Redis Pub/Sub | 저장하지 않고 수신 확인이 없어 구독자가 없으면 사라집니다(최대 한 번 전달). 알림 원본·전달 보장에 맞지 않습니다. 웹 헤더 배지 SSE의 인스턴스 간 신호(HM-281)에만 씁니다. 신호를 잃어도 재연결 때 안 읽음 수를 DB에서 다시 받아 복구됩니다. |
  | Redis Streams | 수신 확인은 있지만 메모리 우선이라 최대 1초를 잃을 수 있고, DB 트랜잭션 밖이라 이중 쓰기가 남습니다. |
  | RabbitMQ·SQS | 전달은 지키지만 수신 확인 뒤 메시지가 사라져 이력이 없고, 이중 쓰기 때문에 아웃박스가 여전히 필요합니다. |
  | Kafka | 가장 강하지만 수신자별 읽음 상태 저장소가 아니고 운영 비용이 가장 큽니다. |

- **도입 기준:** 발신 작업을 별도 프로세스로 떼어야 할 때, 외부 시스템이 같은 이벤트를 구독해야 할 때, 분당 수천 건 이상이 계속 발신될 때 별도 ADR로 브로커를 붙입니다. 그때는 Modulith 이벤트 외부화(`@Externalized`)로 RabbitMQ(AMQP)나 SQS에 냅니다. Modulith 외부화는 Kafka·AMQP·JMS·SQS·SNS만 지원하고 Redis는 지원하지 않습니다. PostgreSQL `FOR UPDATE SKIP LOCKED` 대기열은 초당 수천 건까지 감당해 지금 규모에는 여유가 큽니다.
- **인스턴스 수:** 인스턴스 수는 정해지지 않았습니다. 여러 인스턴스가 함께 돌아도 기록 테이블을 공유하고 리스너가 멱등하므로 별도 잠금을 두지 않습니다.

## 영향과 검증

- **운영 스키마:** 기록 테이블은 다른 테이블과 같이 Flyway 마이그레이션(`V1__init.sql`, [ADR-005](005-schema-migration.md))이 만들고, 발신 대기열 `notification_deliveries`도 Flyway 마이그레이션이 만듭니다. Modulith의 자동 생성(`spring.modulith.events.jdbc.schema-initialization.enabled`)은 모든 프로필에서 끕니다. 기록 테이블 정의는 spring-modulith-events-jdbc 2.1.1 jar 안의 `org/springframework/modulith/events/jdbc/schemas/v2/schema-postgresql.sql`·`schema-postgresql-archive.sql`과 같습니다. 테이블이 없으면 모듈 리스너로 가는 이벤트를 발행하는 업무 트랜잭션이 실패할 것으로 봅니다(운영 DB로 확인하지 않음). Modulith 버전을 올릴 때 스키마 버전이 바뀌었으면 새 버전 마이그레이션으로 따라갑니다. `notification_deliveries`는 팀 ERD에 없어 ERD에 추가해야 합니다.
- **수동 처리:** 계속 실패하는 발행은 원인을 고치면 대기 시간 상한(30분) 안에 다음 재전송으로 처리됩니다. 타입을 찾지 못해 남은 행은 이전 타입을 되살려 배포하거나 내용을 확인한 뒤 지웁니다.
- **커밋 후 리스너 전체:** Modulith는 기록 대상과 무관하게 모든 커밋 후 리스너(`@TransactionalEventListener`)를 감싸 실행 전에 별도 트랜잭션으로 발행 상태를 갱신하려 합니다. 기록하지 않는 리스너도 DB 연결을 쓰고, 그 갱신이 실패하면 리스너가 돌지 않습니다.
- **검증:** `EventPublicationRegistryIntegrationTest`(Testcontainers PostgreSQL)가 기록·보관·롤백·실패·재전송·대기 시간 증가·횟수 제한 없음·멈춘 발행을, `EventResubmissionPropertiesTest`가 대기 시간 계산과 설정 검사를, `FailedEventPublicationResubmitSchedulerTest`가 주기 작업의 예약 실행을, `ApplicationProfileConfigurationTest`가 모든 프로필에서 Modulith 스키마 초기화가 꺼져 있는지와 재전송·발신 대기열 처리의 활성화·로그 수준을 확인합니다. 테스트의 기록 테이블과 발신 대기열도 Flyway 마이그레이션이 만듭니다. 발신 대기열은 `PushDeliveryDispatchIntegrationTest`(두 디스패처 동시 실행에서 1회 발신, 횟수 제한 없는 재시도, 점유 만료 회수, 건너뜀·실패, 숨긴 알림), `NotificationDeliveryPersistenceAdapterTest`(알림 저장 트랜잭션 참여, 동시 집기, 점유 만료, 늦은 결과 버림), `DispatchPushDeliveriesServiceTest`, `NotificationDeliveryTest`, `RetryBackoffTest`가 확인합니다. 여러 인스턴스 프로세스의 동시 실행과 운영 DB의 마이그레이션 적용은 실행으로 확인하지 않았습니다.
- **소비 측 멱등:** 알림은 같은 일(받는 계정·종류·작업·일어난 시각)의 알림이 이미 있으면 다시 만들지도 푸시하지도 않고, 동시에 처리되면 유일 제약이 한쪽을 막습니다([notification 문서](../domain/notification.md#notification-implementation)).
- **남은 일:** 실제 FCM과 기기로의 발신은 로컬 스텁으로만 확인했습니다(`FcmPushSenderTest`). 개발 빌드 앱에서의 수신 확인은 FCM 자격 증명을 넣은 뒤 합니다.
