# ADR-003: 조직 도메인의 소속·계약과 총관리자 모델

- 상태: Accepted
- 기준일: 2026-09-28
- 관련 작업: [HM-258](https://humanistired.atlassian.net/browse/HM-258), [HM-260](https://humanistired.atlassian.net/browse/HM-260)
- 관련 결정: [ADR-001](001-backend-architecture.md#배포와-모듈-경계)

## 배경

기존 기획 초안은 기사를 직원 소속의 역할로 표현하고 역할 전환을 허용했다. HM-258은 직원 소속과 회사별 기사 계약을 구분하며, 같은 회사에서는 비활성을 포함해 한 계정이 둘 중 하나만 가지도록 확정했다. 관리자와 총관리자는 같은 개념이므로 직원 `role`과 회사 소유자 필드를 함께 두면 권한 원본이 중복된다.

## 결정

- 서버 회사 명칭은 `Organization`을 유지한다. 직원 소속은 `Membership`, 회사별 기사 계약은 `Technician`, 참여 요청은 `ParticipantRequest`이며 후속 DB 매핑 이름은 `participant_request`다.
- 인증 경계의 식별자는 `accountId`, 조직 내부 외부 계정 참조는 자체 `AuthAccountId(Long)` / `authAccountId`다. 다른 모듈의 내부 타입을 가져오지 않는다.
- `Membership`과 `Technician`, `StaffType`과 `TechnicianType`은 각각 별도 모델·ID로 둔다. 유형은 선택이며 최소 활성 유형 개수 제한은 없다. 값의 규칙이 같은 이름·색상 값객체만 공유한다.
- 직원·기사 유형 관리는 목록을 포함해 현재 활성 총관리자에게만 허용한다. 유형 이름은 같은 회사·같은 종류 안에서 비활성 유형까지 포함해 중복을 금지한다.
- 유형 삭제는 비활성 관계를 포함한 현재 지정이 있으면 거부하고, 미사용이면 활성 여부와 관계없이 물리 삭제한다. 과거 지정 이력은 저장하지 않고 연결도 자동 해제하지 않는다. 삭제 모달과의 충돌은 현재 지정 보호를 우선하는 이 정책으로 해소하며 작업 유형 삭제는 별도 결정한다.
- 총관리자는 회사의 필수 `ownerMembershipId` 하나로 표현한다. 직원 `role`은 두지 않는다. 같은 회사의 활성 직원만 총관리자가 될 수 있고 위임 전에 비활성화할 수 없다.
- 조직 도메인은 Spring·JPA·Application·Adapter에 의존하지 않는다. 개별 모델은 자체 불변식을, 순수 `ParticipationPolicy`는 전달받은 현재 관계에 대한 중복 판정을 소유한다.
- 기사 참여 시각은 계약 생성 시각 `contractedAt`으로 사용한다. 별도 참여일은 두지 않는다. `last_active_at`의 활동 의미·갱신 주체는 후속 작업에서 합의한다.

## 영향과 제약

직원↔기사 전환과 기사 유형의 직원 교차 지정은 제공하지 않는다. 회사 생성과 최초 총관리자 소속 생성은 Application이 한 트랜잭션에서 처리한다. 참여 요청 승인과 관계 생성은 후속 Application에서 원자적으로 처리해야 한다. 조직·계정별 관계 조회는 비활성을 제외하지 않으며 동시 생성·승인 및 위임·비활성화 충돌을 저장소가 제어해야 한다. 메모리 정책 검사만으로 DB 전체의 중복을 보장하지 않는다.

회사와 직원 소속은 ID를 시퀀스에서 선발급해 함께 저장한다. 회사의 총관리자 소속과 소속의 회사는 서로를 참조하므로 PostgreSQL 지연 FK로 커밋 시 참조 무결성을 확인한다. 회사 코드와 회사·계정별 직원 소속은 DB unique 제약을 둔다. 현재 보조 SQL은 로컬·테스트의 `create-drop`에만 적용하며 운영 적용은 마이그레이션 결정에서 다룬다.

직원·기사 유형도 별도 테이블·시퀀스와 회사별 이름 unique 제약을 사용한다. 직원 소속의 유형 FK는 `ON DELETE RESTRICT`로 삭제·지정 경합에서 참조를 보호한다. 유형 변경·삭제는 유형 행을 쓰기 잠금으로 읽으며, HM-264의 신규 지정은 같은 행을 공유 잠금으로 읽고 활성 상태를 검사해야 한다.
기사 계약 영속성이 없으므로 현재 기사 유형 사용 포트는 미사용을 반환한다. HM-263에서 계약 테이블·유형 FK와 비활성 계약을 포함한 실제 사용 조회를 함께 도입하고, 삭제 FK 충돌을 사용 중 출력 포트 예외로 변환해야 한다. 이때까지 기사 계약의 참조 무결성 검증이 구현된 것으로 보지 않는다.

회사 정보 조회는 현재 활성 총관리자에게만 허용한다. 비소속·비총관리자·비활성 소속과 회사 부재는 같은 403으로 처리하여 회사 존재 여부를 노출하지 않는다. 조회 결과에는 회사 코드를 포함하지 않는다.
정보 수정은 회사 행을 `PESSIMISTIC_WRITE`로 잠근 뒤 총관리자를 확인한다. 이후 총관리자 위임과 수정이 같은 회사 행을 잠그면 두 처리가 직렬화된다. 수정은 이름·선택 업종만 바꾸며 코드와 총관리자 참조를 보존한다.
조회와 수정의 결과 의미가 같으므로 조회가 소유한 `OrganizationDetailsInfo`를 두 입력 포트가 공유한다. 결과 구조를 중복 정의하지 않고 함께 유지하며 command/query 입력 계약은 분리한다.

업종은 확정된 6종을 사용한다. 색상은 사용자 요청에 따라 임시 번호 1~8로 두고 실제 색상 매핑을 TODO로 남긴다. 회사 코드는 8자 대문자 Crockford Base32(`0-9A-HJKMNP-TV-Z`, I·L·O·U 제외) 형식을 검증한다. 생성 Application은 순수 무작위 발급 후 중복 후보를 최대 5회까지 다시 만들며 DB unique 제약으로 동시 충돌을 최종 방어한다. 코드 변경·폐기 정책은 후속 계층의 책임이다.

## 검증

Spring Context 없는 조직 도메인 테스트에서 이름 경계·상태 전이·유형 소유권·총관리자 위임과 비활성화·비활성 포함 중복을 확인한다. `ArchitectureTest`와 `ModularityTest`가 내부 계층 및 모듈 의존성을 검사한다. 상세 동작의 원본은 [조직 도메인](../domain/organization.md#organization)이다.

유형 관리 서비스 테스트는 권한·회사 범위·오류 순서와 상태 변경·삭제를 확인한다. PostgreSQL 테스트는 이름 유니크 경합·수정 충돌·직원 유형 FK 삭제 제한·행 잠금과 저장 상태 복원을, 모듈 조립 테스트는 입력 포트를 통한 실제 생성·수정·조회·상태 변경·삭제를 확인한다. 신규 지정 유스케이스와 비활성화의 통합 경합 검증은 HM-264에 남아 있다.
