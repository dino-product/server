# ADR-007: 사진 파일 저장 방식

- 상태: Accepted
- 기준일: 2026-10-21
- 범위: 사용자가 올리는 파일(지금은 완료보고 사진·현장 사진)의 업로드·연결·조회·삭제 표시 방식과 서버·저장소의 책임 분리. 버킷·IAM·수명 주기 규칙은 `dino-product/infra` 레포가 소유합니다. 사진 개수·용량·권한 같은 제품 규칙은 Notion 정책서가 원본입니다([기획 원본 색인](../planning/README.md#planning)).
- 관련: [ADR-001](001-backend-architecture.md)(모듈 경계·영속성·이벤트), [ADR-003](003-planning-source-of-truth.md)(제품 규칙 원본), HM-353

## 배경과 목적

완료보고 사진과 현장 사진은 업로드를 먼저 마친 파일의 식별자로 받아 왔지만 업로드 방식이 정해지지 않아 저장소가 없었고, 조회 응답의 사진 주소는 임시 어댑터의 가짜 주소였습니다. 사진은 장당 수십 MB이고([현장 수행] 정책 §6 FLD-004), 서버는 노드 메모리가 작고 CloudFront 경유 요청은 30초 안에 끝나야 해서 사진 바이트를 서버로 받지 않아야 합니다. 저장소 장애나 서버 재시작이 있어도 작업에 연결된 사진이 사라지는 일(끊긴 참조)은 없어야 하고, 연결되지 못한 파일(고아)은 남아도 됩니다.

## 결정

- **직접 업로드:** 클라이언트가 S3 presigned PUT으로 `incoming/{fileId}`에 직접 올립니다. 서버는 바이트를 다루지 않습니다. 발급 응답은 `fileId`, `uploadUrl`, `requiredHeaders`(클라이언트가 그대로 붙일 헤더), `expiresAt`이며 URL은 10분 뒤 만료됩니다(`app.media.storage.upload-url-ttl`). 서명에는 `Content-Type`과 `Content-Length`를 넣어 발급 때 밝힌 형식·크기 그대로만 올릴 수 있게 합니다.
- **권한은 도메인 엔드포인트, 저장은 범용 모듈:** 업로드 URL은 사진을 쓰는 업무의 엔드포인트가 권한을 확인한 뒤 발급하고, 업무 상태 조건은 같은 트랜잭션에서 확인합니다(완료보고 사진은 배정된 기사가 작업중 작업에, 현장 사진은 그 발주사의 총관리자·직원이). 완료보고 사진은 형식·크기 오류(400)를 상태 오류(409)보다 먼저 알리려고 발급(`media`의 형식·크기 확인) 뒤에 작업중인지 확인하며, 작업중이 아니면 트랜잭션이 롤백돼 발급 기록이 남지 않고 주소도 돌려주지 않습니다. 그 엔드포인트가 범용 `media` 모듈에 용도·최대 크기를 넘기고, `media`는 허용 형식(설정 `app.media.image-content-types`, 이미지 시그니처를 확인할 수 있는 형식만)과 크기를 확인해 `uploaded_files`에 PENDING 기록을 남깁니다. 파일을 아무나 내려받는 범용 `GET /files/{id}`는 두지 않습니다.
- **연결은 S3 먼저, DB 나중:** 등록·기본정보 수정·완료보고 제출이 파일 식별자를 받으면, 업무 트랜잭션을 시작하기 전에 `media`가 요청자가 올린 같은 발주사·같은 용도의 PENDING 파일인지 확인하고, HeadObject로 존재·크기·Content-Type을, 앞 16바이트 range GET으로 이미지 시그니처(JPEG·PNG·WebP·HEIC/HEIF)를 확인한 뒤 `media/{orgId}/{fileId}`로 복사합니다. range GET과 복사에는 HeadObject의 ETag를 조건으로 붙여(`If-Match`, `x-amz-copy-source-if-match`), 확인하는 사이 같은 키에 다른 파일을 다시 올려도 확인하지 않은 바이트가 연결 위치로 가지 않게 합니다(그 사이 바뀌거나 지워졌으면 업로드 안 됨). 복사할 때 대상 메타데이터는 원본을 쓰지 않고 바꿔(형식은 기록한 값, `Cache-Control: private`·내려받기 주소 유효 시간만큼의 `max-age`, `Content-Disposition: inline`), 업로더가 서명 밖에 붙인 헤더가 내려받기 응답에 쓰이지 않게 합니다. 태그도 원본을 가져오지 않고 비워(`REPLACE`), 만료 표시 같은 원본 태그가 연결된 사진에 옮겨져 수명 주기 규칙에 지워지는 일이 없게 합니다. 그다음 업무 트랜잭션 안에서 작업 저장과 함께 파일을 ATTACHED로 바꿉니다. S3 호출은 DB 트랜잭션 밖에서 하므로 저장소 지연이 DB 연결을 붙잡지 않습니다. 복사 뒤 업무가 실패하면 파일은 PENDING으로 남고(고아), 같은 요청을 다시 보내면 복사를 반복하고 연결합니다. 이미 같은 대상(작업·용도)에 연결된 파일은 다시 확인하지 않고 성공으로 봅니다. 확인 실패(형식·크기·업로드 안 됨)는 바로 오류로 끝내지 않고 업무 유즈케이스가 공통 오류 순서의 입력 검증 자리에서 알립니다.
- **조회는 권한을 통과한 응답에서만:** 작업 상세·완료보고 조회처럼 이미 권한 검사를 통과한 응답에서만 `media/{orgId}/{fileId}`의 presigned GET URL(10분, `app.media.storage.download-url-ttl`)을 붙입니다. 서명은 저장소를 부르지 않지만 자격 증명을 얻지 못하면 실패하므로, 발급과 같이 저장소 장애(503)로 알립니다.
- **삭제는 표시만:** 서버에는 객체 삭제 권한(DeleteObject)이 없습니다. 기본정보 수정으로 빠진 현장 사진은 같은 트랜잭션에서 EXPIRED로 바꾸고, 커밋 뒤 비동기로 객체에 태그 `status=expired`를 붙입니다. 실제 삭제는 버킷 수명 주기 규칙이 합니다. 커밋 전에 태그를 붙이지 않는 것은 업무가 롤백되면 아직 연결된 사진이 지워지기 때문이며, 태그를 붙이지 못하면 객체가 남을 뿐입니다. `incoming/`은 수명 주기 규칙이 1일 뒤 지웁니다.
- **기록:** `uploaded_files`(id UUID, 발주사·업로더 계정 식별자, 용도, 객체 키, 형식, 크기, 상태 PENDING·ATTACHED·EXPIRED, 연결 대상, 생성·연결 시각, 보관 기한 `retain_until`)는 `media`가 소유합니다. 작업 쪽 사진 테이블은 파일 식별자만 둡니다. 보관 기간 상한은 `MEDIA_RETENTION_MAX_DAYS`로 받아, 용도별 보관 기간(`app.media.retention-days`)이 상한을 넘으면 기동에 실패합니다. 지금은 용도별 보관 기간이 정해지지 않아 비어 있고, 보관 배치는 후속 작업입니다.
- **기술:** AWS SDK for Java v2(`s3`, presigner)를 BOM으로 관리합니다. 자격 증명은 기본 체인(배포 환경은 노드 역할·IMDS), API 호출 제한 시간은 5초(시도당 3초)입니다. 복사(CopyObject)만은 S3 서버 쪽 복사 시간이 객체 크기에 비례해, 요청마다 호출·시도 제한 시간을 `app.media.storage.copy-timeout`(기본 60초, `api-call-timeout` 이상)으로 바꿉니다. 시도당 3초를 그대로 두면 큰 사진의 복사는 다시 보내도 매번 시간 초과(503)로 끝나기 때문입니다. 저장소 장애는 어댑터가 경고 로그와 호출 타이머 `media.storage.calls`(작업·결과·상태 코드 태그)로 남겨, 사용자에게는 503으로만 보이는 원인을 운영에서 구분합니다. 엔드포인트 재정의와 path-style 설정으로 로컬은 Compose의 LocalStack, 저장소 어댑터 테스트와 사진 흐름 통합 테스트는 LocalStack Testcontainers를 씁니다. 그 밖의 테스트는 저장소에 닿지 않는 주소를 둡니다(업로드 기록이 없는 식별자는 저장소를 부르기 전에 거부됨).
- **공유 계약(infra와 동일):** 환경 변수 `MEDIA_BUCKET`, `MEDIA_REGION`, `MEDIA_RETENTION_MAX_DAYS`. 객체 키 `incoming/{fileId}`, `media/{orgId}/{fileId}`. 앱 권한은 두 접두사의 PutObject·GetObject, `media/*` PutObjectTagging, 두 접두사로 제한한 ListBucket이며 DeleteObject는 없습니다. 복사가 원본 태그를 읽지 않으므로 `incoming/*` GetObjectTagging은 필요 없습니다(infra에 남아 있어도 동작에는 영향 없음). 서버는 ListBucket이 있어 없는 키의 HeadObject가 403이 아니라 404로 온다고 보고 404만 "아직 올라오지 않음"으로 봅니다. 403은 이 전제나 다른 권한이 어긋난 설정 오류이므로 업로드 전으로 가리지 않고 저장소 장애(경고·지표)로 드러냅니다.

## 검토한 대안

- **서버 경유 multipart 업로드:** 사진 바이트가 노드 메모리·디스크와 CloudFront 30초 제한을 거쳐야 하고, 장당 수십 MB × 12장 요청이 흔해 버리기 어렵습니다.
- **PVC(노드 디스크):** 단일 노드 k3s라 노드 교체 때 사진이 사라질 위험이 있고 백업·용량 관리를 따로 해야 합니다.
- **클러스터 안 MinIO:** 저장 데이터의 내구성을 직접 책임져야 해 PVC와 같은 문제가 남고 운영할 구성 요소가 늘어납니다.
- **PENDING을 객체 태그로만 관리(DB 기록 없음):** 연결할 때 태그를 바꾸다 실패하거나 순서가 어긋나면 수명 주기 규칙이 연결된 사진을 지울 수 있습니다(끊긴 참조). 접두사(`incoming/`·`media/`)와 DB 상태로 나누면 연결된 사진은 만료 규칙 대상이 아닙니다.

## 영향과 검증

- 클라이언트는 발급 → PUT → 업무 요청의 세 단계로 사진을 올리고, 발급 때 형식·크기를 밝혀야 합니다. 응답의 사진 주소는 10분 뒤 만료되므로 화면은 응답을 다시 불러 갱신합니다.
- 업무 유즈케이스 중 사진을 받는 것(작업 등록·기본정보 수정·완료보고 제출)은 저장소 확인을 트랜잭션 밖에서 먼저 하고, 업무 처리와 연결은 내부 트랜잭션 빈에서 합니다.
- 저장소 어댑터 테스트가 LocalStack으로 presigned PUT·HeadObject·range GET·복사·태그·presigned GET을 확인하고, 서명 헤더에 `content-type`·`content-length`가 들어가는지, 확인한 뒤 다시 올린 객체의 읽기·복사가 ETag 조건으로 막히는지, 복사한 객체의 응답 헤더가 고정되고 원본 태그가 옮겨지지 않는지 확인합니다. 사진 흐름 통합 테스트는 발급부터 연결·조회 URL까지 실제 업로드로 확인합니다. 어댑터 단위 테스트는 복사 요청에만 `copy-timeout`이 붙고 다른 호출은 클라이언트 제한 시간을 쓰는지 확인합니다. 실제 S3에서 큰 사진(완료보고 40MiB)의 복사와 12장 확인·복사가 CloudFront 오리진 응답 대기(30초) 안에 끝나는지는 측정하지 않았습니다.
- 기획 확인이 필요한 항목: 클라이언트 압축 업로드 여부, HEIC 허용과 웹 표시, EXIF 위치 정보 제거(지금은 원본 그대로 저장), 현장 사진 장당 용량(JOB-003, 정해질 때까지 설정 `SCHEDULE_SITE_PHOTO_MAX_BYTES`로 두고 비우면 저장소 한도만 적용), 사진 보관 기간과 취소된 작업의 사진 처리.
