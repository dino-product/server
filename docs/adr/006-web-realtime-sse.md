# ADR-006: 웹 실시간 갱신(SSE와 Redis Pub/Sub)

- 상태: Accepted
- 기준일: 2026-10-26
- 범위: 사무실 웹 화면에 변경 신호를 보내는 방식, 연결 관리(상한·유지·수명·종료), 인스턴스 사이 신호 전달. 구현 결정의 원본은 [realtime 문서](../domain/realtime.md#realtime-implementation)입니다. 기사 앱 푸시는 범위 밖입니다([알림] §5).

## 배경과 목적

진행 보드는 실시간 갱신이 요구되고([현황 파악] 정책 §6), 기사가 수락·시작·완료하면 사무실에 바로 보여야 합니다([현장 수행] 정책 §5·§13). 지금 화면은 다시 조회해야만 바뀐 내용을 봅니다. 인프라는 CloudFront → Traefik → orbit-server(k3s, replicas 1, 롤링 배포 때 두 파드가 잠깐 공존)이고 Redis가 클러스터 안에 있습니다(HM-281 설계).

## 결정

- **서버 전송 이벤트(SSE)를 씁니다.** 서버 → 화면 한 방향이면 충분하고, 일반 HTTP 응답이라 CloudFront·Traefik·Spring MVC 서블릿과 Spring Security 체인을 그대로 씁니다. 브라우저 `EventSource`는 Authorization 헤더를 보낼 수 없어 화면은 fetch 기반 클라이언트로 Bearer 토큰을 붙입니다. 웹소켓은 양방향이 필요 없고 업그레이드·인증·프록시 설정을 따로 둬야 해서 택하지 않았습니다.
- **신호에는 식별자와 시각만 담고 화면이 REST로 다시 조회합니다.** 권한·필드 규칙을 조회 API 한 곳에 두고, 놓친 신호는 다시 연결한 뒤의 재조회와 화면의 주기 조회(60초)로 메웁니다. 그래서 신호를 저장하거나 다시 보내지 않습니다.
- **발주사 단위 스트림 하나를 화면들이 함께 씁니다.** 화면마다 연결을 열지 않아 탭 하나당 연결이 하나입니다.
- **연결은 인스턴스 메모리에만 두고 상한·유지·수명을 서버가 관리합니다.** 인스턴스 상한 2,000(초과 503·`Retry-After`), 계정 상한 5(가장 오래된 연결을 닫음), 15초 유지 신호(CloudFront 오리진 응답 대기 30초), 30분 수명(Access Token 1시간 안에서 다시 인증, 연결마다 최대 10% 앞당김), 5초 쓰기 한도입니다. 종료할 때는 정상 종료(30초)보다 먼저 모든 연결에 `reconnect`를 보내고 닫습니다.
- **인스턴스 사이 전달은 Redis Pub/Sub 채널 하나로 합니다.** 커밋된 변경만 신호로 보내고, 모든 인스턴스가 구독해 자기 메모리의 연결에 전달합니다. 이미 쓰는 Redis로 롤링 배포 중 공존하는 파드와 이후 확장을 함께 다룹니다. Pub/Sub은 저장하지 않아 구독하지 않던 인스턴스는 신호를 받지 못하지만, 위의 재조회로 메웁니다. Redis Streams·Kafka는 다시 보낼 필요가 없어 택하지 않았습니다. 신호 발행은 이벤트 발행 기록([ADR-004](004-event-publication-registry.md)) 대상이 아닙니다. 늦게 다시 보낸 신호는 의미가 없기 때문입니다. 그래서 커밋 뒤 처리를 `@TransactionalEventListener`가 아니라 일반 리스너의 커밋 뒤 동작으로 겁니다. Modulith가 커밋 뒤 리스너를 모두 감싸 DB로 발행 상태를 갱신해, 신호마다 DB 연결을 쓰고 DB 장애 때 신호가 멈추기 때문입니다. 보내기는 줄 길이가 정해진 전용 실행기에서 하고, 줄이 차거나 30초보다 오래 기다린 신호는 버립니다. Redis가 멈췄을 때 요청 스레드와 다른 모듈 리스너의 실행기를 붙잡지 않고, 돌아온 뒤 오래된 신호가 한꺼번에 나가지 않게 하기 위해서입니다. 구독은 Redis 없이도 기동을 막지 않도록 연결될 때까지 다시 시도합니다.

## 영향과 검증

- **자원:** 열린 연결마다 응답 버퍼와 전송 줄(최대 100개)을 메모리에 둡니다. 스레드는 전송 8개와 주기 작업 1개입니다. 쓰기가 막힌 연결은 목록에서 빠지지만 막힌 쓰기가 끝날 때까지(컨테이너 쓰기 한도까지) 전송 스레드 하나를 붙잡고, 8개가 모두 막히면 다른 연결의 유지 신호가 늦어집니다. 작은 신호라 커널 버퍼가 흡수해 드물다고 보고 플랫폼 스레드를 씁니다. 상한은 인스턴스마다 따로라 인스턴스를 늘리면 전체 상한도 늘어납니다.
- **보안:** 연결이 끝날 때의 ASYNC 재디스패치만 인가에서 뺍니다. 열린 연결은 소속 변경·토큰 폐기 뒤에도 수명까지 신호(식별자)를 받지만, 다시 조회하는 REST가 권한을 확인합니다.
- **감시:** `realtime.connections`(화면 종류별 열린 연결), `realtime.connections.opened`·`.closed`(사유별)·`.rejected`(사유별)·`.drift`, `realtime.signals.published`(종류·결과별)·`.dropped`(종류·사유별)·`.received`(종류·결과별), `realtime.subscription.listening`(구독 중이면 1). 구독이 끊겨도 연결은 유지 신호로 살아 있어 화면은 알아채지 못하고 주기 조회로만 맞춰집니다. 구독 여부는 구독 컨테이너의 상태라 처음 구독이 열리기 전(Redis가 없어 다시 시도하는 중 포함)과 멈춘 뒤에만 0이고, 구독한 뒤 연결이 끊기면 Redis 클라이언트가 다시 연결하는 동안에도 1입니다. 그래서 경보(규칙은 infra 레포)는 세 가지입니다. 열린 연결(화면 종류 합)이 상한의 70%를 넘을 때, 구독 여부 0이 수집 주기 두 번을 넘길 때(기동·종료 때 잠깐 0이 됨), 전체 인스턴스의 발행 성공이 있는데 받은 신호가 없는 인스턴스가 있을 때입니다. 받은 신호 지표는 처음 받을 때 생기므로 시계열이 없으면 0으로 보고, 갓 뜬 인스턴스는 발행 집계 구간에 기동 전 신호가 들어 있으므로 지속 시간을 그 구간보다 길게 둡니다. 정상으로 끝난 연결 요청은 HTTP 요청 시간 지표(`http.server.requests`)에서 뺍니다. 넣으면 30분짜리 요청이 분위수와 경보를 흐립니다. 거부·오류로 끝난 연결 요청은 남깁니다.
- **HTTP:** 본문이 있는 오류 응답은 Accept와 관계없이 JSON이고(응답 형식을 맞출 수 없는 406만 본문 없음) `Retry-After`는 CORS 노출 헤더에 넣습니다(shared). 연결 요청은 `spring.jpa.open-in-view: false`여야 DB 커넥션을 잡지 않습니다.
- **검증:** `InMemoryRealtimeConnectionsTest`가 상한·교체·유지 신호·수명·쓰기 실패·막힌 쓰기(늦은 성공 포함)·전송 거부·종료·재시작을, `RealtimeModuleTest`가 모듈 단독 조립과 커밋 → Redis → 연결 전달을, `RealtimeSignalEventListenerTest`가 커밋·롤백·트랜잭션 밖·예외 격리·줄 가득 참·오래된 신호를, `RedisRealtimeSignalPublisherTest`·`RedisRealtimeSignalSubscriberTest`가 채널 형식을, `RealtimeSignalSubscriptionTest`가 구독·구독 여부 지표와 Redis 없는 기동을, `RealtimeStreamApiIntegrationTest`가 실제 인증과 소속 조회를 거친 연결·거부·JSON 오류·`Retry-After` 노출·교체 뒤 비동기 재디스패치와 작업 등록·알림 읽음·비동기 알림 저장(새 트랜잭션) 뒤의 신호 수신을, `RealtimeStreamControllerTest`가 503과 `Retry-After`·406을 확인합니다. CloudFront·Traefik을 거친 장시간 연결, 여러 인스턴스 동시 실행, 운영 중 Redis 장애와 복구는 실행으로 확인하지 않았습니다.
- **남은 일:** 연결 끊김 표시와 계정 상한 교체 뒤 표시는 기획 결정이 필요합니다([realtime 차이·공백](../domain/realtime.md#realtime-gaps)).
